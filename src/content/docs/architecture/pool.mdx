游戏里的对象生死频繁：一挺机枪每秒 20 发子弹，每发飞半秒；一场爆炸生成几十个碎片；敌人一波一波地刷出来又被消灭。用 `new` 和 `delete` 管理它们，有三个问题：

1. **慢**：每次都要进分配器，找一块合适的内存；
2. **散**：对象散落在堆的各处，遍历时 CPU 不停地等内存；
3. **悬空引用**：导弹记着目标的指针，目标被销毁了，指针还指着那块内存，下一个住进来的对象就成了"目标"。

**对象池**一次性分配好固定数量的槽位，对象在槽位里出生和死亡；**句柄**代替指针，解决悬空引用。本章实现它们，然后测量内存布局对速度的实际影响。

## 对象池：槽位 + 空闲列表

空闲的槽位用一个链表串起来，"下一个空闲槽位"的编号就存在空闲槽位自己身上（侵入式链表），不需要额外的内存。创建：从链表头取一个；销毁：放回链表。都是 O(1)，对象的地址永远不变。

<CppSnippet file="architecture/pool/pool.h" region="pool" />

稳态 N 个 64 字节的对象，每次随机销毁一个、再创建一个，每对操作的用时：

| N | new / delete | 池（LIFO） | 池（FIFO） | SlotMap |
|---|---|---|---|---|
| 1 000 | 18.1 ns | 1.9 ns | 1.9 ns | 6.7 ns |
| 10 万 | 36.6 ns | 3.9 ns | 4.2 ns | 12.0 ns |
| 100 万 | 106.8 ns | 23.1 ns | 23.1 ns | 70.1 ns |

- **池比 new/delete 快 4.6～9.5 倍**。池的创建和销毁只是改几个整数；分配器要找合适大小的空闲块、维护元数据，还要考虑线程安全。
- 对象多了以后两者都变慢，主要是随机访问的缓存不命中：100 万个 64 字节的对象（64 MB）远远超出了缓存。
- macOS 的分配器对小对象已经很快（一对操作几十纳秒）。真正让 new/delete 成为问题的往往不是单次的速度，而是下面要讲的**散**和**悬空**。

## 句柄：编号 + 代数

只记槽位编号（或者指针）不够：目标死后，槽位被新对象占用，编号仍然"有效"。办法是给每个槽位一个**代数**（generation）：槽位每被释放一次，代数加一。句柄同时记下编号和代数，取对象时代数对不上，说明原来的对象已经死了。

### 代数会回绕

代数是有限位的整数。b 位的代数，同一个槽位被重用 2^b 次后回到原来的值，旧句柄又"有效"了。多久会发生？

| 场景 | 空闲列表 | 8 位代数 | 16 位代数 |
|---|---|---|---|
| 1024 个槽位存活 512 个，随机销毁、创建 | LIFO | 126 381 次创建 | 3363 万次 |
| 同上 | FIFO | 265 521 次 | 5000 万次内未发生 |
| 512 个长寿对象 + 一颗子弹每帧创建、销毁 | LIFO | **256 次** | 65 536 次 |
| 同上 | FIFO | 131 072 次 | 3355 万次 |

- **LIFO + 一个频繁生死的对象是最坏情况**：刚释放的槽位最先被重用，子弹每次都住进同一个槽位，8 位代数 256 帧（60 fps 下 4 秒）就回绕一次；16 位也只要 18 分钟。
- **FIFO 让重用分散到所有空闲槽位**，回绕推迟了 512 倍（空闲槽位的数量）。代价是重用"冷"的槽位，缓存局部性差一点。
- 32 位代数在最坏情况下也要 2³² 帧（60 fps 下 2.3 年）才回绕，实际中可以不考虑。如果为了把句柄塞进 32 位而压缩代数（比如 20 位编号 + 12 位代数），就要认真算一算。
- 随机销毁时，LIFO 并不比 FIFO 差多少（只差约 2 倍）：被随机选中的槽位本来就分散。

## 遍历：空槽的代价

池的缺点是遍历：要逐个槽位看是否存活。存活率低时，遍历的代价由容量而不是存活数决定。

**SlotMap** 换一种做法：对象紧凑地存放在 dense 数组里，删除时用交换删除（5.4 节）保持连续；句柄指向一个间接层（sparse），里面记着对象现在在 dense 的哪个位置。遍历是连续的，代价是对象会移动（不能长期持有指针），按句柄访问多一次间接。

<CppSnippet file="architecture/pool/pool.h" region="slotmap" />

遍历所有存活对象、更新位置（每个对象 64 字节，只读写其中 16 字节），每个存活对象的用时：

| 布局 | 1 万 | 10 万 | 100 万 |
|---|---|---|---|
| vector&lt;Entity&gt; | 0.90 | 0.91 | 1.60 |
| unique_ptr，分配顺序 | 0.77 | 0.81 | 1.69 |
| unique_ptr，运行一段时间后 | 0.78 | 0.82 | **4.75** |
| std::list | 1.56 | 1.83 | 2.07 |
| 池，100% 存活 | 0.80 | 0.86 | 2.00 |
| 池，50% 存活（随机分布） | **4.90** | 5.80 | 6.02 |
| 池，50% 存活（空槽集中） | 1.39 | 1.60 | 3.12 |
| 池，10% 存活 | 10.3 | 13.9 | 14.8 |
| SlotMap | 0.88 | 0.91 | 1.53 |

单位：纳秒 / 存活对象。

- **存活一半的池慢了 6 倍，原因不是缓存**。池里一半是空槽，读的内存只多一倍，用时却多了 6 倍。对照实验：同样 50% 存活，但把空槽集中在后半段，用时只有 1.39 ns。区别在于 `if (alive)` 这个分支：随机分布时 CPU 每两次就猜错一次，每次猜错要清空流水线（十几个周期）。这是一个容易被误判为"缓存问题"的**分支预测**问题。
- **SlotMap 和 vector 一样快**：dense 数组本来就是连续的。存活率经常变化、又需要频繁遍历的对象（子弹、粒子），SlotMap 比池更合适。
- **按指针遍历，只有在对象很多、堆被打乱之后才明显变慢**。1 万、10 万个对象时，unique_ptr 和 vector 几乎一样快：分配器按顺序给出相邻的地址，而且数据装得进缓存。100 万个对象、运行一段时间（随机重建 400 万次）之后，才比 vector 慢 3.0 倍。"指针一定慢"的说法太绝对，但对象多、生命周期长的游戏，堆迟早会变成这样。
- std::list 在 1 万、10 万个对象时慢一倍左右：每个节点多了两个指针，遍历要先读出下一个节点的地址才能继续（指针追逐，CPU 无法提前发出下一次读取）。

### 按句柄访问

随机按引用访问一个对象（读一个字段）的用时：

| N | 裸指针 | 池的句柄 | SlotMap 的句柄 |
|---|---|---|---|
| 1 000 | 0.71 | 0.68 | 0.77 |
| 10 万 | 1.30 | 2.39 | 2.18 |
| 100 万 | 6.09 | 12.0 | 17.0 |

单位：纳秒。对象少时（全在缓存里），句柄检查几乎免费。对象多时，池的句柄要先读槽位的代数和 alive，再读对象，SlotMap 还要多读一次 sparse，每多一次随机访问就多一次缓存不命中。

## 内存布局：缓存行

CPU 从内存读数据的最小单位是**缓存行**：读一个字节，整行都会被读进缓存。所以真正决定速度的，是"读进来的字节里有多少是有用的"。

<Demo name="cache_lines" title="缓存行" label="图 6.1b" caption="遍历 64 个对象，只读每个对象的 16 字节热数据（位置和速度）。一格是 8 字节，一行是 512 字节，粗竖线是缓存行的边界。朱红是用到的字节，灰底是读进来的缓存行。AoS：64 字节的对象连续存放，读进 64 行，只有 25% 有用。hot/cold：热数据单独一个数组，读进 16 行，100% 有用。pointers：对象散落在堆上，读进的行数和 AoS 一样，但每次都跳到不相邻的地方（jumps），硬件预取难以预测。pool 50%：每个槽位都要看一眼 alive 标志，于是空槽所在的行也被读进来了。切换 64 B 和 128 B 看缓存行的大小对每种布局的影响。" />

### 成员的排列

同样五个成员，从 40 字节变成 24 字节，一条缓存行能装下的对象多了 2/3。按从大到小排列成员几乎没有代价。

### 缓存行有多大

`sysctl hw.cachelinesize` 在 Apple M3 上报告 128 字节，而 x86 是 64 字节。用步长实验来验证：在 256 MB 的缓冲区里每隔 S 字节读一个字节。只要 S 不超过缓存行，读进来的行数就一样多，总时间应该不变；超过之后，每翻一倍，读的行数减半。

| 步长 S | 访问次数 | 总时间 | 每次访问 |
|---|---|---|---|
| 4 | 6711 万 | 20.5 ms | 0.31 ns |
| 16 | 1678 万 | 5.46 ms | 0.33 ns |
| 32 | 839 万 | 4.80 ms | 0.57 ns |
| 64 | 419 万 | 5.07 ms | 1.21 ns |
| 128 | 210 万 | 6.07 ms | 2.90 ns |
| 256 | 105 万 | 3.34 ms | 3.19 ns |
| 512 | 52 万 | 1.72 ms | 3.28 ns |

- 步长 4～16 时瓶颈在计算本身（每次访问不到半纳秒）。
- **32～128 字节总时间基本不变，256 开始减半**：从内存读数据的单位确实是 128 字节。

### 伪共享

多线程时还有一个现象：两个线程写的变量不同，但在同一条缓存行上，缓存行就在两个核之间来回传递（**伪共享**）。常见的建议是把每个线程的数据对齐到 64 字节。M3 的缓存行是 128 字节，64 够吗？

4 个线程，各自对自己的计数器做 5000 万次原子加，计数器之间相隔 spacing 字节：

| 间隔 | 用时 |
|---|---|
| 4 字节 | 1792 ms |
| 32 字节 | 643 ms |
| 64 字节 | 146 ms |
| 128 字节 | 111 ms |
| 256 字节 | 112 ms |

- **64 字节就消除了大部分伪共享**：从 1792 ms 降到 146 ms，快 12 倍。
- **但 128 字节还要再快 24%**，之后不再变化。
- 间隔 32 字节时（四个计数器都在同一条 128 字节的行里）已经比 4 字节快 2.8 倍，说明核与核之间争抢的主要单位表现得像 64 字节，128 字节的边界只带来较小的额外代价。我原本以为 128 字节的缓存行意味着间隔 64 字节和 4 字节一样慢，实测并非如此。
- Apple clang 的 `std::hardware_destructive_interference_size` 是 256，`hardware_constructive_interference_size` 是 64。写跨平台代码时，用这个常量（或者直接用 128）比硬编码 64 更稳妥。

<Aside type="caution" title="关于时间">
本章的时间在 Apple M3 上测得，测量时机器负载在 8～30 之间波动（同时运行着其他程序），每项取多轮中最快的一次。绝对值偏大，各方案之间的比例可信；两次完整测量的结论一致。
</Aside>

## 测试

`pool_test.cpp`：

- **池**：LIFO 和 FIFO 各 5 万次随机创建、销毁，与参照（句柄 → 值的 map）对照：存活数、取到的值一致；所有旧句柄都失效；重复销毁被拒绝；forEach 恰好访问存活的对象；构造和析构次数配平（池析构时销毁剩下的对象）；满了返回无效句柄。
- **空闲列表的顺序**：LIFO 先重用最后释放的槽位，FIFO 先重用最早释放的。
- **代数回绕**：8 位代数、一个槽位，第 256 次重用时旧句柄复活（不早也不晚）；随机销毁、创建时 FIFO 至少要 256 × 32 次创建。
- **SlotMap**：5 万次随机操作与参照对照；dense 数组恰好是所有存活对象；旧句柄失效。
- **缓存模型**：四种配置（行大小、行数、组相联度）各 20 万次访问，与"每组一个链表做 LRU"的参照逐次比对命中与否。

变异测试：故意改坏 21 处，第一轮发现 18 处。漏掉的 3 处都是"正常使用时不会出错"的情况：

- **判断句柄有效时不看 alive**：旧句柄的代数已经对不上，所以随机测试发现不了。但一个从未用过的槽位代数是 0，句柄 (3, 0) 就会被当作有效，拿到一块从未构造过的内存。补上"新池里未用过的槽位都无效"。
- **SlotMap 删除时不清空槽位的位置**：同理，代数挡住了所有正常的旧句柄。补上"空槽位即使代数猜对了也无效"。
- **SlotMap 不重用空槽位**：功能完全正确，只是槽位数组无限增长（内存泄漏）。补上"槽位数不超过同时存活的峰值"。

补上后 21 处全部被发现。

## 常见陷阱

| 现象 | 原因 | 解决 |
|---|---|---|
| 导弹追着一个刚刷出来的敌人跑 | 存了指针或下标，目标死后槽位被重用 | 句柄 = 编号 + 代数 |
| 用了句柄，偶尔还是追错 | 代数位数太少，LIFO 让同一个槽位反复重用 | 32 位代数；或者 FIFO 空闲列表 |
| 存活率低时遍历很慢 | 逐个槽位判断 alive，分支预测失败 | SlotMap 连续存放；或者按位图批量跳过 |
| SlotMap 里存的指针失效 | 交换删除移动了对象 | 只长期持有句柄，指针只在一帧内使用 |
| 结构体比成员加起来大很多 | 成员之间的对齐空洞 | 成员从大到小排列 |
| 多线程计数反而更慢 | 不同线程的数据在同一条缓存行上 | 每个线程的数据对齐到缓存行（在 Apple 芯片上用 128） |
| 池满了 | 容量估计不足 | 记录峰值；按块扩容（每块地址不变），不要 realloc 整个数组 |

## 练习

1. **按块扩容**：池满了就再分配一块同样大小的槽位，句柄的编号 = 块号 × 块大小 + 块内编号。为什么不能直接扩大 `std::vector`？
2. **位图遍历**：用一个 64 位整数记录 64 个槽位是否存活，遍历时用"找最低位的 1"跳过空槽。50% 和 10% 存活率下，比逐个判断快多少？
3. **句柄压缩**：把编号和代数压进一个 32 位整数（比如 20 + 12 位）。按本章的回绕实验，在"一颗子弹每帧生死"的最坏情况下多久回绕？
4. **对象池 + 析构顺序**：一个敌人销毁时要通知所有锁定它的导弹。用句柄和不用句柄，各需要怎样的代码？哪种更容易出错？
5. **测一测你的机器**：在 x86 机器上运行步长和伪共享实验，缓存行是否是 64 字节？伪共享在多少字节时消失？
