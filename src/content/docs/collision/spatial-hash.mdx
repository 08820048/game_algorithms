## 问题：两两测试太多了

前三篇回答的都是"**这两个**形状是否相交"。可游戏里要问的是"**哪些**物体在相交"：弹幕游戏里的几千颗子弹、即时战略游戏里的几百个单位、粒子系统里上万个粒子。

最直接的做法是两两测试：

<CppSnippet file="collision/spatial_hash/spatial_hash.h" region="brute" />

n 个物体要测试 n(n-1)/2 对。1000 个物体约 50 万对，16000 个物体就是 1.28 亿对。即使每次 AABB 测试只要零点几纳秒，后者实测也要 324 毫秒，是一帧 16.7 毫秒的 20 倍。

可是这 1.28 亿对里，真正相交的只有 5303 对。绝大多数物体相隔很远，根本不必测试。

所以碰撞检测通常分两个阶段（见 2.1 开头的表格）：

- **宽相**（broad phase）：用很粗糙但很快的方法，找出**可能**相交的物体对，排除绝大多数不可能相碰的。
- **窄相**（narrow phase）：只对这些候选对做精确测试（AABB、SAT、GJK）。

本篇和后面两篇讲宽相。这一篇介绍最简单、在很多场景下也最快的一种：把世界划成格子。

## 思路：只和邻居比

把世界划分成边长相同的正方形格子。每个物体放进它的包围盒覆盖的所有格子里。两个物体如果相交，它们的包围盒一定有公共部分，也就一定**共享至少一个格子**。

所以只需要在每个格子内部两两测试。物体分布均匀、格子大小合适时，每个格子里只有寥寥几个物体，总测试次数大约与物体数成正比。

### 第一版：每个格子一个列表

<CppSnippet file="collision/spatial_hash/spatial_hash.h" region="naive" mark={['std::sort(out.begin(), out.end());', 'out.erase(std::unique(out.begin(), out.end()), out.end());']} />

有一个细节：一个物体可能横跨好几个格子。两个都横跨格线的物体会在多个格子里相遇，同一对就被报告多次。这一版的办法是最后排序去重。

超出世界边界的物体被"夹"进最外圈的格子。结果仍然正确，只是边缘的格子会变挤。

几个值得做的小实验：

1. 对比右侧的两条横条：120 个物体两两测试要 7140 次，网格只需要两百次左右。
2. 把 **cell** 调到最小（16）和最大（112），观察网格测试次数和 cells / object（每个物体平均占几个格子）怎么变化。格子太小，每个物体要放进很多格子；格子太大，每个格子里的物体太多。
3. 找两个跨越格线、互相重叠的盒子，悬停在它们共享的几个格子上：红线只在其中一个格子里出现。这就是下文的"参考格子"去重。
4. 打开 **big**，加入三个大物体。悬停在大物体覆盖的格子里，看看每个格子要多做几次测试。
5. 切换到 **hash**，把 buckets 调到 31 左右。悬停在一个空格子上，它可能仍然有内容：那是同一个桶里其他格子的物体。再把 buckets 调大，看测试次数如何回落。

## 更好的写法：计数排序与参考格子

第一版的思路没问题，但在实现上有两处可以改进：每个格子一个 `std::vector`，内存分散；去重需要对所有结果排序。下面的写法同时解决这两点。

### 用计数排序重建

物体每帧都在动，最简单的做法是每帧从头重建。重建分两遍：第一遍数出每个格子里有几个物体，求前缀和得到每个格子在数组中的起止位置；第二遍把物体编号填进去。

<CppSnippet file="collision/spatial_hash/spatial_hash.h" region="build" />

重建之后，所有格子的内容连续存放在一个数组 `entries_` 里，第 s 个格子的内容是 `entries_[start_[s] .. start_[s+1])`。整个过程只有几次顺序扫描，第一帧之后不再分配内存。

### 用参考格子去重

两个盒子相交时，它们的交集也是一个盒子。取交集的左上角，它所在的格子称为这一对的**参考格子**。交集同时属于两个盒子，所以两个物体都覆盖参考格子，一定都在那个格子的列表里。规定**只在参考格子里报告**这一对，就能保证每对恰好报告一次：

<CppSnippet file="collision/spatial_hash/spatial_hash.h" region="pairs" mark={['if (overlaps(b[i], b[j]) && refSlot(b[i], b[j]) == s) out.push_back({i, j});']} />

判断只需要几次比较和一次乘法，不需要任何额外的集合，结果也不必排序。

同样的办法可以用于**区域查询**：找出与某个矩形重叠的所有物体，比如爆炸的范围、鼠标框选、AI 寻找附近的敌人：

## 空间哈希：没有边界的网格

均匀网格需要事先知道世界有多大，并为每个格子分配存储。世界很大而物体集中在一小块区域时，大部分格子都是空的，却仍然要占内存、要在重建时清零、在找物体对时逐个扫过。

**空间哈希**（spatial hash）把格子坐标 `(x, y)` 经过哈希函数映射到固定数量的**桶**里。只有桶需要存储，世界可以无限大，格子坐标也可以是负数。

上面的实现把"格子 → 存储位置"的映射单独抽了出来，网格和哈希共用其余所有代码：

<CppSnippet file="collision/spatial_hash/spatial_hash.h" region="indexers" />

代价是**哈希冲突**：两个不相邻的格子可能落进同一个桶。这不影响正确性，因为每对候选仍然要做 AABB 测试，只是多出一些不必要的测试。演示里 hash 模式下的虚框格子就是冲突的格子。

参考格子的去重仍然成立。改成"只在参考格子所在的**桶**里报告"即可：两个物体都覆盖参考格子，所以都在那个桶里。还有一个新问题要处理：同一个物体覆盖的两个格子可能落进同一个桶，如果它在桶里出现两次，同一对就会被报告两次。`forEachSlot` 里的 `stamp_` 记录每个桶最后放进了哪个物体，避免重复放入。

<Aside type="caution" title="漏掉这一步，除了重复还会很慢">
把 `stamp_` 的检查删掉，单元测试立刻报错：查询结果里出现重复。更隐蔽的是性能：测试中有一个场景是桶数为 1、格子边长 1.5，再加上边长 300 的大物体。最大的物体覆盖约四万个格子，全部挤进同一个桶，于是桶里有约一百万个条目，两两测试的次数是条目数的平方。原本几秒跑完的单元测试，两分钟后仍未结束。有了 `stamp_`，每个物体在一个桶里最多出现一次。
</Aside>

## 实测：快了多少？

在边长 4~12 的随机盒子上测量每帧的耗时，包括重建和找出所有物体对。物体数变化时，场地面积同比例变化，密度保持不变：

| 物体数 | 相交的对 | 两两测试 | 第一版网格 | 网格 | 空间哈希（2n 个桶） | 网格的测试次数 |
|---|---|---|---|---|---|---|
| 1000 | 363 | 1.09 ms | 0.01 ms | 0.02 ms | 0.02 ms | 1490 |
| 4000 | 1304 | 18.4 ms | 0.10 ms | 0.10 ms | 0.10 ms | 5618 |
| 16000 | 5303 | 324 ms | 0.89 ms | 0.76 ms | 0.78 ms | 22758 |
| 64000 | 21382 | 约 5 秒（估算） | 4.02 ms | 3.34 ms | 4.05 ms | 90747 |

- **两两测试的耗时随数量平方增长**：物体数乘以 4，耗时变为 16 倍。网格大致是线性的。16000 个物体时，网格快了 400 多倍。
- **第一版网格并不慢**。只比计数排序版慢 15%~20%，物体少时甚至更快。`std::vector::clear()` 不释放内存，第一帧之后同样不再分配；相交的对很少，排序去重的开销也很小。真正的提升来自"只测试同格的物体"这个思路，存储布局的优化是次要的。
- **重建比找物体对更贵**：16000 个物体时，重建 0.38 毫秒，找物体对 0.17 毫秒。两万多次 AABB 测试很便宜，把四万多个条目分散写进内存反而更费时间。

### 格子该多大？

同样 16000 个盒子（边长 4~12），只改变格子大小：

| 格子边长 | 每帧 | 测试次数 | 每个物体占几个格子 | 格子数 |
|---|---|---|---|---|
| 3 | 2.30 ms | 35007 | 14.0 | 719104 |
| 6 | 1.05 ms | 22423 | 5.6 | 179776 |
| 12 | 0.68 ms | 22758 | 2.8 | 44944 |
| 24 | 0.57 ms | 36890 | 1.8 | 11236 |
| 48 | 0.84 ms | 85042 | 1.4 | 2809 |
| 96 | 1.62 ms | 246781 | 1.2 | 729 |

格子太小，每个物体要写进很多格子，重建变慢；格子太大，每个格子里的物体太多，测试次数迅速增加。最快的是 12~24，也就是**最大物体尺寸的 1~2 倍**，这也是常见的经验法则。在这个范围内曲线很平坦，不需要精确调整。

### 大小悬殊的物体

把其中 1%（160 个）换成边长 200 的大物体：

| 格子边长 | 每帧 | 测试次数 | 每个物体占几个格子 |
|---|---|---|---|
| 12 | 1.16 ms | 101428 | 6.1 |
| 24 | 1.17 ms | 79180 | 2.7 |
| 48 | 1.22 ms | 117672 | 1.6 |
| 96 | 2.05 ms | 280562 | 1.3 |
| 200 | 4.84 ms | 934493 | 1.1 |

两两测试仍然要 332 毫秒，网格仍然快 280 倍，但比所有物体大小相近时慢了一倍。这时"按最大物体选格子大小"的法则不再适用：按 200 选格子是最慢的一档，因为其余 99% 的小物体全挤在一起了。格子按小物体选，大物体就要写进几百个格子。

单一尺寸的格子无法同时照顾大物体和小物体。下一篇的四叉树让格子按需分裂，大物体和小物体自然落在不同的层级。它是否真的更快，下一篇会用同样的场景实测（剧透：没有想象中那么简单）。

### 桶的数量

空间哈希的桶数怎么定？16000 个物体、格子边长 12：

| 桶数 | 每帧 | 测试次数 |
|---|---|---|
| 均匀网格（44944 个格子） | 0.61 ms | 22758 |
| 0.25n = 4000 | 1.67 ms | 275444 |
| 0.5n = 8000 | 1.24 ms | 148220 |
| n = 16000 | 0.92 ms | 85743 |
| 2n = 32000 | 0.85 ms | 54262 |
| 4n = 64000 | 0.79 ms | 38226 |
| 16n = 256000 | 0.94 ms | 26737 |

即使有 2n 个桶，测试次数仍是网格的 2.4 倍。起初我怀疑是哈希函数质量不好，换成 MurmurHash3 的混合函数后，测试次数几乎一样（54164 对 54262）。真正的原因是：每个物体平均覆盖 2.8 个格子，被占用的格子约有 4.5 万个，比 3.2 万个桶还多，冲突不可避免。

所以**桶数应该参照被占用的格子数，而不是物体数**。被占用的格子数大约是"物体数 × 每个物体占几个格子"。桶太多也会变慢，因为每次重建都要把所有桶清零、扫一遍。

### 网格什么时候不如哈希

物体分布均匀、世界大小固定时，网格最快。可如果世界很大，物体只集中在一角：

| | 每帧 | 格子 / 桶 | 内存 |
|---|---|---|---|
| 网格，世界与物体分布范围相同 | 0.63 ms | 44944 | 0.4 MB |
| 网格，世界边长 4 倍 | 1.09 ms | 714025 | 5.7 MB |
| 网格，世界边长 16 倍 | 9.44 ms | 11390625 | 91 MB |
| 空间哈希，任意世界大小 | 0.92 ms | 32000 | 0.3 MB |

网格的耗时和内存除了与物体数有关，还随**世界面积**增长；空间哈希只与物体数有关。开放世界、物体会飞得很远的场景（太空游戏、无尽跑酷）应该用哈希。

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`。测试时机器负载很高（load average 20~75），因此每组取 9 次中的最快值，两次独立运行的结论一致。64000 个物体的两两测试没有实际运行，按平方关系从 16000 个的结果估算。代码在 `cpp/collision/spatial_hash/spatial_hash_bench.cpp`。
</Aside>

## 每帧重建，还是增量更新？

另一种做法是只在物体跨越格子时才更新：从旧格子里删除，加入新格子。看起来省事，但需要为每个物体记住它在哪些格子里，删除操作要在列表里查找，格子的内存也重新变得分散。

上面的测试表明，16000 个物体全部重建只要 0.38 毫秒。对于每帧都在运动的物体，全部重建通常更简单也更快。如果场景中大部分物体是静止的（墙、树、建筑），更好的做法是把它们放进一个只建一次的单独结构，每帧只重建运动的物体，再分别查询"运动对运动"和"运动对静止"。

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 同一对物体被处理两次（受到两次伤害、触发两次事件） | 两个物体同时出现在多个格子里 | 参考格子去重，或者对结果排序去重 |
| 空间哈希里偶尔出现重复的对 | 一个物体的两个格子落进同一个桶，被放进去两次 | 插入时检查这个桶最后放进的是不是同一个物体（本文的 `stamp_`） |
| 原点附近的格子特别挤 | 用 `int(x / cell)` 计算格子坐标，它向 0 取整，`(-cell, cell)` 整段都落进第 0 格，格子宽度翻倍。结果仍然正确，只是变慢 | 用 `std::floor` |
| 世界边缘处的格子特别挤，变慢 | 超出世界的物体全被夹进最外圈的格子 | 把世界边界设大一些，或者改用空间哈希 |
| 少数大物体让整体变慢 | 大物体覆盖大量格子 | 大物体单独测试，或者用多层网格、四叉树（2.5） |
| 空间哈希比预期慢 | 桶数参照物体数，实际被占用的格子更多，冲突严重 | 桶数取被占用格子数的 1~2 倍 |

## 在游戏中的应用

- **弹幕与粒子**：几千颗大小相同的子弹，是均匀网格最擅长的场景。
- **群体模拟的邻居查询**：Boids、人群、流体粒子（SPH）需要找出半径 r 内的所有邻居。把格子边长设为 r，只需检查自己所在的格子和周围 8 个格子。Matthias Müller 的 Ten Minute Physics 用的正是本文这种计数排序的空间哈希。
- **网络游戏的兴趣管理**：服务器只把玩家附近格子里的实体同步给他，格子边长取视野范围。MMO 服务器常用这种"九宫格"做法。
- **地图编辑器与鼠标拾取**：点击位置所在的格子里只有几个候选物体。
- **2D 物理引擎**：Chipmunk2D 提供空间哈希作为宽相的选项之一；Box2D 则使用 2.6 节介绍的动态 BVH。

## 练习

1. **邻居查询**：用 `query` 为 2000 个 Boids 找出半径 30 内的邻居（先查询边长 60 的正方形，再按距离筛选）。与两两计算距离的结果对比，并测量速度。
2. **静态与动态分开**：在场景里放 5000 个静止的墙块和 2000 个运动物体。静止物体只建一次网格，每帧只重建运动物体，分别查询"运动对运动"和"运动对静止"。与全部重建相比，快了多少？
3. **网格里的射线**：射线穿过的格子可以按顺序逐个走过（Amanatides 与 Woo 的逐格遍历算法）。用它实现"沿射线找到第一个被击中的物体"，找到之后就可以停止，不必检查更远的格子。
4. **多层网格**：准备格子边长为 8、32、128 的三层网格，每个物体放进"格子不小于自身"的最细一层。物体对需要在本层和所有更粗的层之间查找。用本文"大小悬殊"的场景测试，能否消除大物体带来的减速？
