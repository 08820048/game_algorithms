## 另外两种思路

前两篇的均匀网格和四叉树都在**划分空间**：先把世界切成小块，再看物体落在哪一块。这一篇介绍另外两种思路：

- **Sweep and Prune**（扫描与剪除，简称 SAP）：把物体按 x 坐标**排序**，只有 x 方向上重叠的物体才需要进一步检查。
- **BVH**（Bounding Volume Hierarchy，包围体层次）：把物体**分组**，每组套一个包围盒，组再合成更大的组，形成一棵树。

这两种方法有一个共同点：它们都能利用"物体每帧只移动一点点"这一事实，从上一帧的结果出发增量更新，而不是每帧从头构建。这也是物理引擎青睐它们的原因。

## Sweep and Prune：排序后扫描

两个盒子相交，必须在 x 方向和 y 方向上都重叠。SAP 先只看 x 方向：把所有盒子在 x 轴上的投影区间按左端点排序，然后从左往右扫描。对每个区间，往后看那些左端点落在它范围内的区间，只有它们与它在 x 上重叠；遇到左端点超过它右端的区间就可以停下，因为后面的只会更靠右。

<CppSnippet file="collision/bvh/bvh.h" region="sap" mark={['for (; j > 0 && entries_[j - 1].lo > e.lo; --j, ++swaps) entries_[j] = entries_[j - 1];', 'for (size_t q = p + 1; q < entries_.size() && entries_[q].lo < e.hi; ++q) {']} />

`update` 是 SAP 的关键技巧。物体每帧只移动一点点，上一帧排好的顺序几乎仍然有序。对几乎有序的数组，**插入排序**只需要很少的交换，接近线性时间，比每帧调用 `std::sort` 便宜。这叫利用**时间相干性**（temporal coherence）。

<Aside type="caution" title="扫描时仍要做完整的测试">
x 区间的左端点落在另一个区间之内，看起来已经说明 x 方向重叠了，只需再检查 y。我最初就是这样写的，结果单元测试报错：一个宽度为 0 的盒子恰好落在另一个盒子的左端点上时，两者的左端点相同，排序后它排在后面，被判定为"x 重叠"，而按严格不等式它们并不重叠。所以扫描到的候选对仍然做完整的 AABB 测试。
</Aside>

SAP 的弱点也很明显：**它只在一个轴上筛选**。如果很多物体在 x 上挤在一起（比如所有物体都在一条竖直的长条里），x 区间大量重叠，SAP 就退化成接近两两测试。下文的实测会看到，同一个场景转 90°，SAP 慢了 8 倍。

## BVH：把物体分组

BVH 是一棵二叉树。每个叶子对应一个物体，每个内部节点存放一个包围盒，恰好盖住它的两个孩子。查询时从根节点往下走，与查询区域不重叠的节点连同整棵子树一起跳过：

<CppSnippet file="collision/bvh/bvh.h" region="query" />

它与四叉树的关键区别：四叉树划分**空间**，节点区域互不重叠，跨越分割线的物体只能留在上层；BVH 划分**物体**，每个物体一定在叶子里，代价是兄弟节点的包围盒可能互相重叠。上一篇困扰严格四叉树的跨线问题，在 BVH 里不存在。

### 动态 BVH

静态场景可以一次性建好 BVH（自顶向下按某个轴切分）。游戏里的物体会动、会生成、会销毁，所以物理引擎使用**动态** BVH：支持随时插入、删除、移动物体。下面的实现参考了 Box2D 的 `b2DynamicTree`，包含三个要点。

**1. 胖包围盒。** 叶子存放的不是物体真实的包围盒，而是向外扩大 `margin` 的"胖"盒子。物体在胖盒子里移动时，树完全不需要改动；只有跑出去了，才删除、重新插入：

<CppSnippet file="collision/bvh/bvh.h" region="proxy" mark={['if (containsBox(nodes_[leaf].box, tight)) return false;']} />

**2. 插入时选择最合适的兄弟。** 新叶子要和某个已有节点配对，成为同一个新父节点的两个孩子。配对后，从新父节点到根的所有祖先都要扩大。好的树应该让包围盒尽量小，因为包围盒越小，查询时被访问的概率越低（二维用周长衡量，三维用表面积，这就是**表面积启发式** SAH 的思路）。

插入时从根节点往下走，在每个节点比较三个选择：就在这里配对，或者往左走，或者往右走。往下走时，当前节点及其祖先的扩大是"已经付出"的代价：

<CppSnippet file="collision/bvh/bvh.h" region="insert" />

**3. 旋转保持平衡。** 只按代价贪心插入，树可能变得很不平衡。最坏的情况是物体按坐标顺序依次插入：树退化成一条长链。所以每次插入、删除后，沿着到根节点的路径检查每个节点，左右子树的高度相差超过 1 就做一次旋转，与 AVL 树相同：

单元测试里，1024 个排成一行的盒子按顺序插入，有旋转时树高 10（就是 log₂1024），没有旋转时树高 1023。

### 找出所有物体对

任意两个叶子都有唯一的**最近公共祖先**。所以只需要对每个内部节点，比较它的左子树和右子树之间的物体对：两棵子树的包围盒不重叠，就整体跳过；重叠则把较大的那个拆开，继续比较。

几个值得做的小实验：

1. 把 **margin** 调到 0：几乎每个运动的物体每一步都要重新插入（看 reinserted）。调到 16：重新插入很少，但虚线框变大，tree tests 增加。
2. 关闭 **rotate**：树被重建，高度从 6 左右增加到 10 以上。观察结构图里出现的长链。
3. 悬停在结构图的某个内部节点上：上方高亮它的包围盒。注意兄弟节点的包围盒经常互相重叠，这是 BVH 与四叉树最直观的区别。

5. 在 sap 模式下观察 swaps this frame：大多数帧只有零到几次交换，这就是插入排序便宜的原因。

## 物理引擎里的用法：保留物体对

上面的 `findPairs` 每帧都要遍历整棵树。Box2D 的宽相做得更聪明：**物体对在帧与帧之间保留下来**。每一帧：

1. 删掉胖盒子不再重叠的物体对；
2. 只有本帧被重新插入的物体（跑出了胖盒子）才查询新的伙伴；
3. 其余物体的物体对沿用上一帧的结果。

<CppSnippet file="collision/bvh/bvh.h" region="broadphase" />

这样每帧的工作量只与"移动的物体数"和"物体对的数量"有关，与物体总数无关。在大部分物体静止的场景里（墙、箱子、睡眠中的刚体），这一点非常重要。

## 实测

16000 个盒子（边长 4~12，与前两篇密度相同）连续运动 60 帧，每帧更新结构并找出所有相交的物体对，取三次运行中平均每帧耗时最低的一次。网格和四叉树每帧重建；SAP 和 BVH 增量更新。BVH 的 margin 取 4（下文测出的最优值）。

| 方法 | 所有物体都在动 | 只有 10% 在动 |
|---|---|---|
| 均匀网格（2.4） | 0.91 ms | 0.84 ms |
| 严格四叉树（2.5） | 3.04 ms | 3.03 ms |
| SAP，每帧 `std::sort` | 4.29 ms | 4.23 ms |
| SAP，插入排序 | 3.68 ms | 3.53 ms |
| BVH，每帧重建 | 8.28 ms | 8.15 ms |
| BVH，增量更新 + 遍历整棵树 | 3.69 ms | 2.82 ms |
| BVH，增量更新 + 保留物体对 | 4.57 ms | **0.75 ms** |

- **所有物体都在动时，网格仍然最快**，比其余方法快 3~9 倍。物体大小相近、分布均匀，正是网格的主场。
- **只有 10% 的物体在动时，保留物体对的 BVH 第一次跑赢了网格**。每帧只有 330 个物体跑出胖盒子，只需要为它们做查询。网格不管物体动不动，每帧都要全部重建。
- **增量更新的价值很大**：同样是 BVH，每帧重建要 8.3 毫秒，增量更新只要 3.7 毫秒。
- **SAP 的插入排序只比 `std::sort` 快 4%~15%**。时间主要花在扫描上：正方形场地里，每个物体在 x 上平均与上百个物体重叠，一共 81 万次测试，排序本身只是零头。

### SAP 与场地形状

把同样 16000 个物体放进长宽比 16:1 的长条场地（横版卷轴游戏的典型形状）：

| | 沿长轴（x）扫描 | 同一场地转 90°，沿短轴扫描 |
|---|---|---|
| 均匀网格 | 0.96 ms | 0.88 ms |
| 严格四叉树 | 4.47 ms | 3.82 ms |
| SAP，插入排序 | **1.26 ms**（20 万次测试） | 10.0 ms（326 万次测试） |
| BVH，增量更新 | 4.13 ms | 4.09 ms |

沿长轴扫描时，SAP 比在正方形场地里快了近 3 倍，接近网格；转 90° 后慢了 8 倍。实际使用时，应该选物体分布最分散的那个轴（可以统计各轴上坐标的方差），或者像 Bullet 那样在多个轴上同时维护排序。BVH 和网格对场地形状不敏感。四叉树在长条场地里变慢，是因为它的节点也被拉成了 16:1 的长条。

### 速度与胖盒子

物体越快，越容易跑出胖盒子。同样 16000 个物体全部运动，margin 为 2：

| 每帧移动（像素） | SAP 插入排序 | 每帧交换次数 | BVH 增量 | 每帧重新插入 |
|---|---|---|---|---|
| 0.25 | 3.54 ms | 10840 | 2.80 ms | 1598 |
| 1 | 3.64 ms | 43337 | 4.55 ms | 5966 |
| 4 | 3.65 ms | 173188 | 8.36 ms | 15509 |
| 16 | 3.98 ms | 689336 | 8.53 ms | 16000 |

SAP 对速度不敏感：交换次数随速度增加，但交换很便宜。BVH 则在物体跑得比 margin 快时，几乎每帧要把所有物体重新插入一遍，耗时翻倍。

margin 本身也要权衡（速度约每帧 1 像素）：

| margin | 0 | 0.5 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|---|---|
| 每帧 | 7.78 ms | 7.88 ms | 6.11 ms | 4.62 ms | **3.67 ms** | 3.93 ms | 7.84 ms |
| 重新插入 | 16000 | 15509 | 10883 | 5966 | 3195 | 1596 | 765 |

margin 太小，重新插入太频繁；太大，胖盒子之间的假重叠太多，遍历要做的测试增加。最优值大约是物体几帧内的移动距离。Box2D 的做法是 margin 取一个固定的小值（0.1 米），再把胖盒子沿速度方向额外延长，让快速物体也不必每帧重新插入。

### 旋转有多重要

把 16000 个静止的盒子依次插入：

| 插入顺序 | 旋转 | 树高 | 插入总耗时 | 找物体对 |
|---|---|---|---|---|
| 随机 | 有 | 17 | 5.7 ms | 1.93 ms |
| 随机 | 无 | 95 | 14.8 ms | 2.40 ms |
| 按 x 排序 | 有 | 16 | 4.6 ms | 2.77 ms |
| 按 x 排序 | 无 | 502 | 91.3 ms | 2.08 ms |

不平衡的树主要伤害**插入**：每次插入都要从根走到底，树高 502 时插入慢了 20 倍。有些意外的是，找物体对的耗时几乎不受影响，按顺序插入、没有旋转的那棵树甚至还快一些。遍历的代价取决于兄弟节点包围盒的重叠程度，而不是树的深度。但对于动态 BVH，物体每帧都在重新插入，所以旋转是必需的。

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`。机器负载较高（load average 10~40），每种方法运行三次 60 帧的模拟，取平均每帧耗时最低的一次；两次独立运行的结论一致。代码在 `cpp/collision/bvh/bvh_bench.cpp`。
</Aside>

## 宽相方法怎么选

三篇文章、五种方法，总结一下实测结果：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 物体大小相近、全部在动（子弹、粒子、群体） | 均匀网格 / 空间哈希 | 在所有"全部运动"的测试中最快 |
| 大部分物体静止，少数在动（典型的物理关卡） | 动态 BVH + 保留物体对 | 工作量只与移动的物体有关 |
| 物体大小相差悬殊、世界无边界 | 动态 BVH 或四叉树 | 不需要选格子大小 |
| 物体沿一个方向铺开（横版卷轴、赛道） | SAP | 实现最简单，沿长轴扫描很快 |
| 静态场景，以查询、射线检测为主 | BVH（一次性构建）或松散四叉树 | 大范围查询可以整块跳过 |

这也解释了为什么 Box2D、Bullet 等通用物理引擎选择动态 BVH 作为宽相：它在任何场景下都不会太差，物体大小、世界大小都没有限制，而且在"大部分物体静止"的真实游戏场景中表现最好。PhysX 走了另一条路，宽相是 SAP 的改进版本（SAP、MBP、ABP 可选），场景查询则使用 AABB 树。

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| SAP 偶尔多报一对 | 只检查了 y，没检查 x 的边界情况（宽度为 0 的盒子） | 扫描到的候选对做完整的 AABB 测试 |
| SAP 突然变得很慢 | 物体在扫描轴上挤在一起 | 选择分布最分散的轴，或者在多个轴上排序 |
| BVH 插入越来越慢 | 没有旋转，树退化成长链 | 每次插入、删除后沿路径做旋转 |
| BVH 每帧都在大量重新插入 | margin 太小，或者物体跑得比 margin 快 | 增大 margin，或者沿速度方向延长胖盒子 |
| 保留的物体对越积越多，越来越慢 | 只添加新的物体对，忘了删除胖盒子已经分开的 | 每帧先删掉胖盒子不再重叠的物体对（`update` 的第 1 步） |
| 删除物体后程序崩溃 | 物体对列表里还保留着它 | 删除叶子时同时删除相关的物体对（Box2D 在销毁代理时清理接触） |

## 在游戏中的应用

- **2D / 3D 物理引擎的宽相**：Box2D 的 `b2DynamicTree`、Bullet 的 `btDbvt` 都是动态 BVH；Bullet 也提供多轴 SAP（`btAxisSweep3`），PhysX 的宽相则是 SAP 的改进版本。
- **射线检测与可见性查询**：游戏里的"射线检测"大多走 BVH。光线追踪（包括 GPU 硬件光追）的核心数据结构也是 BVH。
- **横版游戏与赛道**：物体沿一个方向分布，SAP 简单又快。
- **静态关卡几何**：一次性构建、离线优化的 BVH，用于角色控制器的碰撞查询。

## 练习

1. **射线检测**：为 `DynamicTree` 加上 `rayCast`。从根节点开始，用 2.1 的射线–AABB 测试判断是否进入节点，并记录目前找到的最近命中，跳过比它更远的节点。
2. **多轴 SAP**：同时在 x 和 y 上维护排序，每帧选择 x 重叠数更少的那个轴扫描。在本文的长条场地里测试，确认它在两个方向上都快。
3. **沿速度方向延长胖盒子**：插入时把胖盒子沿本帧的位移再延长 k 倍（Box2D 取 k = 4）。在"速度与胖盒子"的测试中，重新插入的次数能减少多少？
4. **自顶向下构建**：为静态场景实现一次性构建的 BVH：按包围盒较长的轴，以物体中心的中位数把物体一分为二，递归下去。比较它与逐个插入得到的树的内部节点周长之和（`internalPerimeter`），以及找物体对的速度。
