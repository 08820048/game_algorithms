## 问题：格子该多大？

上一篇的均匀网格很快，但有一个要事先决定的参数：格子大小。实测表明，它应该取最大物体尺寸的 1~2 倍。问题是：

- 物体大小相差悬殊时，没有一个尺寸能同时照顾大物体和小物体；
- 物体分布不均匀时，有的格子挤满了物体，有的格子空着，却同样要占内存。

**四叉树**（quadtree）换了一种思路：先用一个格子盖住整个世界，哪个格子里的物体太多，就把它等分成四块，再继续往下分。物体密集的地方格子细，空旷的地方格子粗，不需要事先指定格子大小。三维中每次等分成八块，就是**八叉树**（octree）。

## 让格子按需分裂

每个节点负责一个正方形区域（`cell`）。叶子节点直接存放物体；当叶子里的物体超过 `splitCount` 个时，它就分裂成四个孩子，把能装进孩子的物体移下去。

<CppSnippet file="collision/quadtree/quadtree.h" region="insert" />

孩子的编号用二进制位表示：第 k 位决定第 k 个坐标轴上取低的一半还是高的一半。二维有 2 位，所以是 4 个孩子；三维有 3 位，就是 8 个孩子。本文的代码对维数 D 写成模板，`Tree<2>` 是四叉树，`Tree<3>` 是八叉树，其余代码完全相同。

<CppSnippet file="collision/quadtree/quadtree.h" region="child" mark={['if (b.max[k] <= mid) continue;', 'if (b.min[k] >= mid) { c |= 1 << k; continue; }', 'return -1;']} />

注意 `return -1`：一个物体只有完全落在分割线的同一侧，才能放进孩子。**跨越分割线的物体只能留在当前节点**，即使这个节点已经分裂了。这是四叉树最重要的特点，也是它最大的麻烦，下文会反复遇到。

每帧重建整棵树。物体用链表挂在节点上（`next_[i]` 是同一节点里的下一个物体），重建时只需要清空数组，不会为每个节点单独分配内存：

## 找出所有相交的物体对

每个物体只挂在一个节点上，而且完全位于这个节点的区域之内。所以一个物体只可能与三类物体相交：同一节点里的、祖先节点里的、后代节点里的。不同分支里的物体，区域互不重叠，不可能相交。

于是可以深度优先遍历整棵树，一路记下"祖先节点里的物体"：每个物体只和同一节点的其他物体、以及祖先物体比较。每一对恰好比较一次，不需要去重：

<CppSnippet file="collision/quadtree/quadtree.h" region="descend" mark={['if (overlaps(b[stack_[k]], child.cell)) stack_.push_back(stack_[k]);', 'if (overlaps(b[i], child.cell)) stack_.push_back(i);']} />

高亮的两行是一个关键的优化：往下传递祖先物体时，只传与孩子区域重叠的那些。

我第一版没有做这个过滤，结果 16000 个物体要做 325 万次测试，比网格慢 8 倍多。原因正是跨线的物体：根节点上有 109 个物体压在世界的中线上，每一个都要和其余全部 16000 个物体比较。加上过滤后，压在竖线上的物体只会传给左右两侧真正碰到它的孩子，测试次数降到 16 万次，耗时从 5.4 毫秒降到 2.9 毫秒。

## 亲手试一试

<Demo name="quadtree" title="四叉树" label="图 2.5" caption="盒子在场地里运动，每一步重建四叉树，细线是节点的分割。平时，黄色粗框的物体跨越了分割线，留在上层节点。鼠标处是一个区域查询（红框）：浅色是访问过的叶子，黄色粗框是做了盒子测试的物体，红色是命中。悬停时，鼠标所在的叶子以黑框标出，松散树下用虚线画出它的松散边界。" />

几个值得做的小实验：

1. 在 **strict** 模式下，注意右侧的 above leaves：120 个物体里，通常有 40% 左右不在叶子里。它们都压在某条分割线上，线越粗，所在的节点越靠上。
2. 把鼠标移到场地一角做查询：压在中线上的物体离鼠标很远，却仍然被测试了（黄色粗框），因为它们挂在根节点上，每次查询都要经过根节点。
3. 切换到 **loose**：above leaves 立刻变成 0。查询时被测试的物体也少了很多。但右侧的 tree tests（找出所有物体对的测试次数）反而变多了，原因见下一节。
4. 拖动 **split**：1 表示叶子里多于 1 个物体就分裂，树很深；16 时树只有两三层。
5. 打开 **big**：大物体总是挂在很上层的节点上。

## 松散四叉树

跨线的物体之所以麻烦，是因为分割线的位置是固定的：一个很小的物体，只要碰巧压在根节点的中线上，就只能留在根节点。

Thatcher Ulrich 在 *Game Programming Gems*（2000）中提出了**松散四叉树**（loose quadtree）：每个节点的边界向四周各扩大半个格子，边长变为原来的 2 倍。相邻节点的松散边界互相重叠，物体只要**中心**落在某个孩子的区域内、大小不超过这个孩子的格子，就一定装得进它的松散边界。

<CppSnippet file="collision/quadtree/quadtree.h" region="child" mark={['float center = (b.min[k] + b.max[k]) * 0.5f;', 'float reach = half * opt_.looseness;  // 松散边界的半边长']} />

这样一来，物体能下到多深只取决于它的**大小**，与位置无关。实测中，16000 个物体在严格树里有 35% 不在叶子里，在松散树里全部在叶子里。

代价是：兄弟节点的松散边界互相重叠，**不同分支里的物体也可能相交**，上面的祖先栈办法会漏掉它们。单元测试专门验证了这一点：在松散树上使用祖先栈，2D 有 31 个、3D 有 25 个随机场景漏掉了物体对。松散树只能退回到"每个物体做一次区域查询"：

## 实测：和网格比

用上一篇完全相同的场景：16000 个盒子，每帧重建并找出所有相交的物体对。网格的格子边长取 12（上一篇测出的最优值附近），四叉树最多 10 层、叶子超过 8 个物体就分裂。括号里是 AABB 测试次数：

| 场景 | 相交的对 | 两两测试 | 网格 | 严格四叉树 | 松散四叉树 |
|---|---|---|---|---|---|
| 大小相近（4~12） | 5269 | 326 ms | 0.63 ms（2.3 万） | 2.87 ms（16 万） | 8.54 ms（29 万） |
| 1% 是边长 200 的大物体 | 22925 | 347 ms | 1.27 ms（10 万） | 3.19 ms（20 万） | 11.3 ms（43 万） |
| 聚成 8 团 | 64609 | 185 ms | 2.95 ms（27 万） | 6.50 ms（104 万） | 14.6 ms（53 万） |

结论可能和你想的不一样：**这三个场景里，网格都比四叉树快 2~5 倍**。上一篇我曾期待四叉树能解决大物体的问题，实测并没有。

原因有三点：

- **树有额外的开销**。网格算一次除法就知道物体在哪个格子；四叉树要从根节点一层层往下走，每层做几次比较。严格树重建要 1.12 毫秒，网格约 0.4 毫秒（上一篇）。
- **跨线的物体**。严格树的测试次数是网格的 7 倍，主要来自那 35% 不在叶子里的物体。
- **松散树找物体对很慢**。它的重建最快（0.49 毫秒），可是每个物体都要从根节点开始做一次查询，找物体对花了 7.2 毫秒。

"聚成 8 团"本应是四叉树的强项，可是团内物体非常密集，真正相交的就有 6 万多对，网格的格子再挤，也只是在测试那些本来就靠得很近的物体。

调整 `splitCount` 也改变不了结论：从 1 到 32，严格树始终在 2.7~3.1 毫秒之间（大小相近的场景）。

### 四叉树的优势在哪里

那四叉树还有什么用？换两个场景再看。

**物体大小相差两个数量级**：16000 个盒子，边长从 2 到 512 均匀分布在对数尺度上（每个数量级的物体一样多）：

| | 每帧 | 测试次数 |
|---|---|---|
| 两两测试 | 404 ms | 1.28 亿 |
| 网格，格子边长 8 | 170 ms | 4858 万 |
| 网格，格子边长 32 | 19.2 ms | 444 万 |
| 网格，格子边长 128 | **10.8 ms** | 118 万 |
| 网格，格子边长 512 | 20.2 ms | 257 万 |
| 严格四叉树（无需调参） | 12.3 ms | 190 万 |
| 松散四叉树 | 26.9 ms | 205 万 |

调到最好的网格仍然比四叉树快一点。但网格的耗时在不同格子大小之间相差 16 倍，而四叉树**不需要调任何参数**，就能达到最优网格的九成左右。物体大小无法预知时（比如玩家自己搭建的关卡），这种稳健性很有价值。

**大范围查询**：一次查询的区域越大，网格要扫过的格子就越多；四叉树可以整块跳过不相关的子树，或者整块接受。在大小相近的场景里做区域查询，每次查询的耗时：

| 查询区域边长 | 网格 | 严格四叉树 | 松散四叉树 | 每次查询的盒子测试（严格 / 松散） |
|---|---|---|---|---|
| 10 | 0.03 μs | 0.47 μs | 0.42 μs | 214 / 20 |
| 40 | 0.17 μs | 0.68 μs | 0.59 μs | 231 / 35 |
| 160 | 1.47 μs | 1.60 μs | 1.51 μs | 343 / 141 |
| 640 | 13.3 μs | 6.05 μs | 5.51 μs | 1512 / 1276 |

小范围查询网格快得多；区域边长到 640（约 53×53 个格子）时，四叉树快了一倍多。屏幕范围的视锥剔除、大范围的爆炸伤害、AI 的视野查询，都属于这种情况。

还要注意最后一列：严格树即使查询一个 10×10 的小区域，也要测试 214 个物体，几乎都是挂在路径上各层节点的跨线物体。松散树只要 20 个。**查询为主的场景，松散树更合适；找所有物体对的场景，严格树更合适。**

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`。机器负载较高（load average 10~35），因此每组取 9 次中的最快值，两次独立运行的结论一致。32000 个物体的三维两两测试按平方关系估算。代码在 `cpp/collision/quadtree/quadtree_bench.cpp`。
</Aside>

## 该选哪一个？

| 场景 | 推荐 |
|---|---|
| 物体大小相近、每帧都在动（子弹、粒子、单位） | 均匀网格或空间哈希（2.4） |
| 物体大小无法预知、相差悬殊 | 四叉树 / 八叉树，或者多层网格 |
| 静态场景、以查询为主（关卡几何、视锥剔除、拾取） | 松散四叉树 / 八叉树，建一次反复查询 |
| 需要逐帧增量更新、物体有大有小 | 下一篇的 BVH（2.6） |

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 越界的物体偶尔查不到 | 严格树只按中线判断放进哪个孩子，没检查物体是否在节点区域之内。世界之外的物体被放进了不包含它的孩子，查询时这个孩子被跳过 | 放进孩子之前，先确认物体完全在节点区域内。本文的单元测试最初就是这样失败的 |
| 少数跨线物体让整体变慢 | 它们留在上层节点，每次都要与整棵子树比较 | 往下传递祖先物体时按孩子区域过滤；或者改用松散树 |
| 很多物体位置相同时，树无限加深 | 叶子永远分不开 | 限制最大深度（`maxDepth`） |
| 松散树漏掉了碰撞 | 用了严格树的祖先栈办法 | 松散树用区域查询找物体对 |
| 树很深时查询反而变慢 | 每层都要比较，叶子里只有一两个物体 | `splitCount` 取 4~16，不要取 1 |

## 在游戏中的应用

- **视锥剔除与遮挡查询**：三维场景用八叉树组织静态几何，一整棵子树在视锥外就整块跳过。早期的很多 3D 引擎都这样做。
- **地形 LOD**：地形按四叉树划分成块，离摄像机近的块细分，远的块合并，这是 CDLOD、Chunked LOD 等地形算法的骨架。
- **大型静态关卡的拾取与查询**：鼠标点选、射线检测、AI 视野。
- **稀疏体素**：体素游戏、全局光照（如稀疏体素八叉树 SVO）用八叉树只存储非空的区域。
- **图像与贴图**：贴图图集打包、四叉树图像压缩，思路相同。

## 练习

1. **双树遍历**：松散树找物体对很慢，是因为每个物体都从根节点开始查询。改为同时遍历两个节点：先比较两个节点的松散边界，不重叠就整块跳过；重叠则比较双方挂着的物体，再递归比较它们的孩子。测一测能比本文快多少。
2. **增量更新**：松散树的优点之一是物体移动一小段后通常仍在原节点的松散边界内，不需要移动。实现 `move(i, newBox)`：仍在边界内就只更新盒子，否则删除再插入。在每帧只有 10% 物体移动的场景里，与全部重建比较。
3. **最近邻**：实现"找离某点最近的物体"。按节点到查询点的距离从近到远访问，用一个优先队列，一旦最近节点的距离超过当前找到的最近物体，就停止。
4. **线性四叉树**：用 Morton 码（交错 x、y 的二进制位）给每个物体编号，按编号排序，同一节点的物体在数组中连续。不用指针就能表示整棵树，比较它与本文写法的重建速度。
