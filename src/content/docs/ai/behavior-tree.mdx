## 问题：状态机的转移是一张网

上一篇的分层状态机解决了重复转移的问题，但留下了几个难点。考虑一个搬箱子的工人：

1. 走到门口；
2. 开门：门没锁就直接开；锁了但有钥匙，就开锁再开门；都不行就踹门，最多踹三次；
3. 进屋拿箱子，搬到外面的放置点；
4. 饿了要先去吃东西；有敌人靠近要立刻逃跑。

用状态机写，"开门"的每一种方式、每一步都是一个状态，每个状态都要知道成功后去哪、失败后去哪。要在"开锁"和"开门"之间加一步"检查门后有没有陷阱"，就得修改前后两个状态的转移。状态之间互相引用，形成一张网。

**行为树**（behavior tree）换了一种组织方式：每个节点只负责自己的事，并向父节点报告结果；怎么组合，由父节点决定。节点之间不需要互相知道。

## 基本概念

行为树每帧从根节点开始**执行**（tick）一次。每个节点被执行后，返回三种结果之一：

- **成功**（Success）
- **失败**（Failure）
- **运行中**（Running）：还没做完，下一帧继续

**叶子**是游戏提供的具体行为：

- **条件**（condition）：检查某件事，立即返回成功或失败。比如"饿了吗"。
- **动作**（action）：做某件事，可能需要好几帧。比如"走到门口"：没到返回运行中，到了返回成功，路被堵死返回失败。

**组合节点**决定怎么执行子节点。最重要的只有两种：

- **顺序**（sequence，记作 →）：从左到右依次执行，**全部成功才成功**；任何一个失败，整个顺序就失败。相当于"并且"：先走到门口，并且开门，并且进屋……
- **选择**（selector，记作 ?）：从左到右依次尝试，**一个成功就成功**；全部失败才失败。相当于"或者"：直接开门，或者用钥匙开，或者踹开。

两者其实是同一段逻辑的两面，只是"继续下一个"的条件相反：

于是搬箱子的工人可以写成：

```
? root                          （选择：从上到下就是优先级）
├─ → flee                       有敌人就逃跑
│    ├─ if enemy near?
│    └─ run away
├─ → eat                        饿了就去吃
│    ├─ if hungry?
│    ├─ go to food
│    └─ eat
├─ → fetch chest                否则搬箱子
│    ├─ go to door
│    ├─ ? open door
│    │    ├─ if door open?
│    │    ├─ → just open:  if not locked? → open
│    │    ├─ → use key:    if have key? → unlock → open
│    │    └─ retry 3: kick door
│    ├─ go to chest
│    ├─ pick up
│    ├─ carry to drop
│    └─ drop
└─ sulk                         实在不行就生会儿闷气
```

读起来几乎就是需求本身。要加一步"检查陷阱"，只需要在 `use key` 的顺序里插入一个节点，其他节点完全不受影响。

## 运行中的节点：记忆与响应

"运行中"带来一个问题：下一帧从哪里继续？

假设工人正在执行"走到门口"（运行中）。下一帧，根节点再次执行：

- **有记忆**（memory）的组合节点记住上次运行中的子节点，直接从它继续，前面已经成功的子节点不再执行。`fetch chest` 应该这样：已经走到门口、开了门，就不要再检查一遍。
- **响应式**（reactive）的组合节点每帧从头开始，重新检查前面的子节点。根节点必须这样：每一帧都要重新确认"有没有敌人""饿不饿"，才能在搬箱子途中及时转去逃跑或吃饭。

### 被打断的节点要收到通知

响应式节点带来了第二个问题。工人正在"搬箱子"，这一帧突然饿了：根节点从头检查，`eat` 分支成功进入运行中，于是根节点不会再执行到 `fetch chest`。可是 `fetch chest` 里那个"运行中"的动作并不知道自己被抛弃了：它可能还占着计时器、还在播放走路动画、还锁定着某个资源。

所以组合节点在返回时，要检查那些**这次没有执行到、上次却还在运行**的子节点，通知它们停下（halt）。halt 会递归地传给它的子孙，动作借此清理自己：

这是行为树实现中最容易遗漏的一点。单元测试专门验证了：响应式顺序的条件失败时，运行中的动作恰好被中止一次；高优先级分支变得可行时，低优先级分支被中止，之后重新开始。

## 装饰节点与并行

**装饰节点**只有一个子节点，用来修改它的结果：

- **取反**（inverter）：成功变失败，失败变成功。
- **重复**（repeat n）：子节点成功 n 次才算成功。
- **重试**（retry n）：子节点失败了就再试，最多 n 次。工人"踹门最多三次"就是它。
- **总是成功**：用于"可选"的步骤，失败也不影响后续。

为了避免一帧之内无限循环，重复和重试每帧最多完成一轮，然后返回运行中。

**并行**（parallel）节点每帧执行所有子节点，成功的数量达到 k 个就成功，不可能再达到就失败；结束时中止仍在运行的子节点。典型用法是"边走边说话"，或者"在 10 秒内找到玩家，否则放弃"（一个子节点找人，另一个子节点计时）。

## 亲手试一试

<Demo name="bt" title="行为树" label="图 3.2" caption="一个搬箱子的工人。右侧是它的行为树：黄色是运行中，墨色是成功，朱红是失败，浅色是这一帧没有执行到的节点。门是红色表示锁着，可以用 locked 和 key 切换门锁和钥匙。鼠标是敌人，靠近时工人逃跑；hungry 让工人立刻饿。" />

几个值得做的小实验：

1. 默认门是锁着的、没有钥匙：工人走到门口的那一帧，`open door` 的前三个分支依次失败，进入 `retry 3` 开始踹门。之后的每一帧，有记忆的 `open door` 直接从 `retry 3` 继续，所以前三个分支显示为浅色。三次都没踹开的话，`fetch chest` 失败，根节点转到 `sulk`，过一会儿再来。
2. 勾选 **key**：下一趟，`use key` 分支成功，工人开锁进门。取消 **locked**：`just open` 直接成功。
3. 工人搬箱子途中按 **hungry**：`eat` 分支立刻接管，正在运行的"搬运"被中止。吃完以后，`fetch chest` 从头开始：工人已经拿着箱子，"走到门口""去拿箱子"等步骤都立即成功，直接继续搬运。动作自己判断"已经做过了"，是让有记忆的顺序被打断后能够顺利重来的关键。
4. 把鼠标移到工人旁边：`flee` 接管。注意 `flee` 是响应式的，鼠标一离开，"有敌人吗"失败，逃跑被中止，工人回去继续工作。
5. 观察 `eat` 分支运行时，`hungry?` 是浅色的：`eat` 是有记忆的顺序，一旦开始吃，就不会因为饥饿值下降而中途放弃。如果把它改成响应式，工人吃到一半（饥饿值降到 70 以下）就会走开。

行为树最常见的写法是"每种节点一个类、虚函数 `tick`、每个角色拥有一整棵节点对象"。我按这种方式独立实现了一个版本，作为对照：

单元测试随机生成 3000 棵树（各种组合节点、装饰节点、有记忆和响应式混合，最深 5 层），叶子的结果由"节点编号和第几次被调用"的哈希决定，两种实现看到的完全一样。每棵树运行 40 帧，比较每一帧的根节点结果、每一次动作调用和每一次中止通知的顺序：155979 个事件（其中 13885 次中止）全部一致。

## 实测

### 每帧开销

一万个工人（与演示相同的树：26 个节点，其中 17 个叶子）各运行 200 帧：

| 写法 | 根节点 | 每个角色每帧 | 每帧执行的节点数 |
|---|---|---|---|
| 每个角色一棵对象树 | 响应式 | 46.6 ns | — |
| 共享定义 | 响应式 | 41.8 ns | 7.0 |
| 每个角色一棵对象树 | 有记忆 | 35.3 ns | — |
| 共享定义 | 有记忆 | 25.0 ns | 3.4 |

这次"共享定义"只快了 10%~40%，远不如上一篇状态机的 5 倍。原因是：每个角色的对象树是一次性连续分配的，彼此挨着放在内存里；而且每帧只执行 3~7 个节点，访问的数据很少。上一篇的状态机，每个角色的定义里有字符串、多个 `std::vector`，分散在内存各处。

### 响应式的代价

响应式根节点每帧都要重新检查所有更高优先级的分支。根节点下有 N 个"条件不满足"的分支，只有最后一个在运行：

| 分支数 N | 1 | 4 | 16 | 64 | 256 |
|---|---|---|---|---|---|
| 响应式 | 6.4 ns | 34.8 ns | 123 ns | 496 ns | 1924 ns |
| 有记忆 | 6.3 ns | 6.8 ns | 7.6 ns | 7.5 ns | 9.1 ns |

响应式的代价随分支数线性增长，每个分支约 7.5 纳秒。对于几十个分支的树，这仍然很便宜；但大型游戏里，一个角色的行为树可能有上百个节点，一千个角色每帧都把所有条件检查一遍，就成了负担。

Unreal 引擎的行为树用**事件驱动**解决这个问题：条件（在 Unreal 里叫装饰器）订阅黑板上的数据，只有数据变化时才重新求值，必要时中止低优先级的分支（"观察者中止"）。平时只执行运行中的那个节点。

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`，取 5 次中的最快值，两次运行的结论一致。代码在 `cpp/ai/bt/bt_bench.cpp`。
</Aside>

## 行为树与状态机

| | 状态机 | 行为树 |
|---|---|---|
| 组织方式 | 状态 + 转移，一张网 | 树，父节点决定怎么组合子节点 |
| 增加一个行为 | 要修改相关状态的转移 | 插入一个节点，其他节点不受影响 |
| "依次做几件事、失败时换个办法" | 每一步一个状态，转移很多 | 顺序 + 选择，直接表达 |
| 优先级与打断 | 外层转移（分层状态机） | 响应式选择，从左到右就是优先级 |
| "记住之前在做什么" | 历史转移 | 不需要：每帧重新判断该做什么 |
| 每帧开销 | 只检查当前状态的转移 | 响应式节点要重新检查前面所有分支 |
| 适合 | 模式少、切换规则清晰（动画、游戏流程） | 行为多、步骤多、需要频繁调整（角色 AI） |

两者并不互斥。常见的做法是：顶层用状态机划分大的模式（巡逻、战斗、死亡），每个状态里用一棵行为树描述具体做什么；或者反过来，在行为树的叶子里使用小状态机。

还有一个概念常与行为树一起出现：**黑板**（blackboard），即树中所有节点共享的数据，比如"最后看到敌人的位置""当前目标"。本文的 `Ctx`（演示中的 `World`）就扮演黑板的角色。

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 被打断的动作没有停下（动画还在播、资源没释放） | 没有中止那些"上次运行中、这次没执行到"的节点 | 组合节点返回前中止它们，halt 递归传递 |
| 角色对紧急情况反应迟钝 | 根节点有记忆，运行中的分支不会被重新检查 | 需要被打断的地方用响应式节点 |
| 角色做事做到一半就放弃 | 响应式节点每帧重新检查条件，条件中途变化 | 一旦开始就要做完的步骤，用有记忆的顺序 |
| 一帧之内卡死 | 重复节点在同一帧里无限循环 | 每帧最多完成一轮，然后返回运行中 |
| 树越来越大，每帧都很慢 | 响应式节点每帧检查所有条件 | 事件驱动：条件只在数据变化时重新求值 |
| 动作之间传递数据很混乱 | 节点之间直接互相引用 | 通过黑板共享数据，节点之间保持独立 |

## 在游戏中的应用

- **《光环 2》**（Halo 2，2004）：Damian Isla 在 GDC 2005 上介绍了它的 AI 架构，这被普遍认为是行为树在游戏界流行的起点。
- **Unreal Engine** 内置了行为树编辑器，使用黑板和事件驱动的装饰器；**Unity** 有 Behavior Designer 等插件，以及官方的 Behavior 包。
- 《孢子》（Spore）等许多游戏使用行为树驱动角色 AI。
- **机器人**：ROS 2 的导航系统 Nav2 也使用行为树组织导航任务，行为树已经从游戏扩展到了机器人领域。

## 练习

1. **黑板与观察者**：给 `Ctx` 加上"版本号"，每次修改数据时递增。让响应式节点只在相关数据的版本变化时才重新检查前面的分支，测量本文"响应式的代价"一节的表格能降低多少。
2. **超时装饰节点**：`timeout(child, seconds)`：子节点运行超过指定时间就中止它并返回失败。用它实现"10 秒内找不到钥匙就放弃"。
3. **子树复用**：把"开门"做成一个可以在多处引用的子树（同一份定义，被两个父节点引用）。注意：同一个子树在两处同时运行时，每处需要自己的运行状态。
4. **用行为树实现上一篇的守卫**：巡逻、搜查、追击、攻击、逃跑、击晕、死亡。比较节点数与分层状态机的转移数；击晕结束后"回到原来的状态"在行为树里是怎么自然实现的？
