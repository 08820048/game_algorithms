## 卷三导读：游戏 AI

前两卷解决的是"怎么走过去"（寻路）和"撞上了怎么办"（碰撞与物理）。这一卷回答另一个问题：**角色该做什么**。

游戏 AI 与学术上的人工智能目标不同。它不追求"最优"，而是追求**可信、可控、可调**：守卫要看起来聪明，但不能聪明到让玩家无路可走；设计师要能看懂 AI 为什么这样做，并且能改。所以游戏 AI 的工具大多很朴素：

| 章节 | 方法 | 回答的问题 |
|---|---|---|
| 3.1 ~ 3.2 | 状态机、行为树 | 角色现在处于什么模式，什么时候切换 |
| 3.3 ~ 3.4 | GOAP、效用 AI | 有多个目标时，选哪一个、怎么达成 |
| 3.5 ~ 3.6 | 转向行为、影响力图 | 怎么移动，怎么理解地图上的局势 |
| 3.7 ~ 3.8 | Minimax、蒙特卡洛树搜索 | 回合制对弈中，下一步怎么走 |
| 3.9 | 视野与感知 | 角色能看到什么 |

这一篇从最基础、也最常用的工具开始：有限状态机。

## 有限状态机

一个守卫的行为可以分成几种**模式**：巡逻、搜查、追击、攻击、逃跑。在每种模式下，它做的事情很简单；复杂的是模式之间的切换：

- 巡逻时看到玩家 → 追击；
- 追击时靠得足够近 → 攻击；离远了 → 继续追击；
- 两秒没看到玩家 → 去最后看到的地方搜查；
- 血量低于 30 → 逃跑；回到 60 以上 → 重新巡逻。

这就是**有限状态机**（finite state machine，FSM）：有限个**状态**，每个时刻处于其中一个；状态之间有**转移**，每条转移有一个条件，条件满足时切换到目标状态。

## 状态爆炸

给守卫加两个"任何时候都可能发生"的事件：

- **死亡**：血量归零，无论在做什么都立即死亡；
- **被击晕**：被闪光弹击中，晕 1.5 秒，**然后回到原来在做的事**。

看 `switch` 版本的开头：死亡和击晕被提到了 `switch` 外面，因为每个状态都需要它们。"血量低就逃跑"也在巡逻、搜查、追击、攻击四个分支里各写了一遍。更麻烦的是"回到原来在做的事"：状态机本身只记得当前状态，被击晕之后就忘了之前在做什么，只能额外用一个 `resume` 变量记住。

如果坚持用纯粹的状态机（只有状态和转移，没有额外的变量），会怎样？

<CppSnippet file="ai/fsm/guard.h" region="flat" />

每个状态都要自己写一遍"死亡""击晕""血量低"。为了让"击晕结束后回到原来的状态"，每个来源都需要一个自己的 `Stunned` 副本：从巡逻被击晕的、从追击被击晕的……一共 5 个。结果是 **11 个状态、33 条转移**。每加一个全局事件，转移数就要乘上状态数。

## 分层状态机

观察一下这些重复的转移：它们其实属于一**组**状态，而不是某一个状态。"血量低就逃跑"对巡逻和搜查都成立，因为它们都属于"平静"；"死亡"对所有活着的状态都成立。

**分层状态机**（hierarchical FSM，HFSM）允许状态嵌套。父状态的转移对它所有的子状态都有效。守卫的行为于是可以组织成：

```
Alive
├─ Active
│  ├─ Calm      ── Patrol, Investigate
│  ├─ Combat    ── Chase, Attack
│  └─ Flee
└─ Stunned
Dead
```

"死亡"挂在 `Alive` 上，一条就够；"击晕"挂在 `Active` 上；"血量低"挂在 `Calm` 和 `Combat` 上。从 `Stunned` 回到 `Active` 时使用**历史转移**：恢复离开 `Active` 时所在的子状态，不需要任何额外的变量。

<CppSnippet file="ai/fsm/guard.h" region="hfsm" />

**11 个状态（其中 7 个叶子）、12 条转移**，而且每条转移都写在它真正所属的地方。

### 实现

状态机分成两部分：**定义**（有哪些状态、哪些转移、进入和退出时做什么）和**实例**（某个角色当前处于哪个状态）。所有守卫共享同一份定义，每个守卫只需要记住自己的当前状态。下文的实测会说明为什么这一点很重要。

<CppSnippet file="ai/fsm/fsm.h" region="def" />

每次更新时，从最外层的祖先到当前叶子，依次检查每一层的转移。**外层优先**：如果"死亡"和"看到玩家"同时满足，挂在 `Alive` 上的"死亡"先被检查到。这是分层状态机最有用的性质之一：紧急情况总能打断日常行为。

<CppSnippet file="ai/fsm/fsm.h" region="update" />

切换状态时，要正确地调用退出和进入动作。从当前叶子往上退出，直到它与目标的**最近公共祖先**；再从公共祖先往下进入，直到目标；如果目标是复合状态，就沿着初始子状态（或者历史记录）继续往下，直到叶子。比如从 `Attack` 被击晕：

- 退出 `Attack`、`Combat`、`Active`（最近公共祖先是 `Alive`，它不退出）；
- 进入 `Stunned`。

1.5 秒后历史转移回到 `Active`：进入 `Active`，它记得上次在 `Combat`；进入 `Combat`，它记得上次在 `Attack`；进入 `Attack`。

<CppSnippet file="ai/fsm/fsm.h" region="change" mark={['if (int p = states[s].parent; p >= 0) lastChild_[p] = s;  // 记下离开时所在的子状态', 'int child = resume && lastChild_[s] >= 0 ? lastChild_[s] : states[s].initial;']} />

单元测试用一个手写的小状态机逐个验证了进入、退出的顺序：最近公共祖先不退出、外层转移优先、目标是自己的祖先时先退出再进入、多层历史能逐层恢复。

## 三种写法真的等价吗

分层状态机、扁平状态机、手写 `switch`，三者应该表现出完全相同的行为。单元测试用随机但有持续性的输入（玩家时而出现时而消失、距离随机游走、偶尔听到声音、偶尔被击晕、挨打和回血）驱动三个守卫，各运行 300 局、每局 1500 帧：

- **45 万帧中，三者所处的状态完全相同**，没有一帧不一致；
- 每个状态都被访问过；击晕结束后恢复到巡逻、搜查、追击、攻击、逃跑的情况分别发生了 83、436、1856、411、137 次，历史转移的每一种情况都被覆盖到了。

这个测试也很能发现错误：把"外层优先"改成"内层优先"、去掉历史记录、退出时不找最近公共祖先，或者让扁平版的某个 `Stunned` 回错了地方，都会立即报错。

## 亲手试一试

<Demo name="fsm" title="分层状态机" label="图 3.1" caption="鼠标就是玩家。守卫沿虚线巡逻，扇形是它的视野，柱子会挡住视线；贴得很近时，不在视野里也会被察觉。点击场地扔一块石头制造声音。flash 是闪光弹，shoot 打掉守卫 25 点血，revive 让它复活。右侧高亮的是当前活动的状态链，下面是最近的状态转移。" />

几个值得做的小实验：

1. 把鼠标移进守卫的视野：它切换到 `Combat`，追过来，靠近后开始攻击。注意右侧：`Alive`、`Active`、`Combat`、`Attack` 一起亮起。
2. 躲到柱子后面：两秒后守卫转为 `Investigate`，走到最后看到你的地方张望一会儿，然后回去巡逻。
3. 在守卫攻击时按 **flash**：它被击晕；1.5 秒后直接回到 `Attack`，而不是从巡逻重新开始。在巡逻时按 flash，恢复后继续巡逻。这就是历史转移。
4. 连按三次 **shoot**：血量低于 30，守卫逃跑。无论它当时在巡逻还是战斗，挂在 `Calm` 和 `Combat` 上的这条转移都会生效。
5. 在守卫逃跑时扔石头：它不理会。逃跑状态没有"听到声音"的转移，这正是我们想要的。

## 实测：通用状态机的代价

一万个守卫、每个运行 100 帧，测量每个守卫每帧的耗时（输入预先生成，只计状态机本身）：

| 写法 | 每个守卫每帧 |
|---|---|
| 手写 `switch` | 4.5 ns |
| 扁平状态机，第一版 | 224 ns |
| 分层状态机，第一版 | 340 ns |
| 扁平状态机，去掉每帧的内存分配 | 95~118 ns |
| 分层状态机，去掉每帧的内存分配 | 174~193 ns |
| 扁平状态机，所有守卫共享一份定义 | **19 ns** |
| 分层状态机，所有守卫共享一份定义 | **25 ns** |

第一版慢了 50~75 倍，原因有两个，都与"状态机"这个概念无关，而是实现上的问题：

- **每帧分配内存**。第一版的 `update` 每次都把当前的状态链放进一个新的 `std::vector`，一帧两次。改成固定大小的数组后快了一倍。
- **每个守卫一份完整的定义**。每个守卫都存了所有状态的名字、所有转移的条件函数，一万个守卫的数据散落在内存各处，几乎每次访问都缓存未命中。验证方法很简单：只用 100 个守卫（数据全部装进缓存）时，同样的代码只比 `switch` 慢 4~6 倍。把定义拆出来、所有守卫共享之后，每个守卫只剩一个当前状态和一小段历史记录，耗时降到 19~25 纳秒。

最终版本仍比手写 `switch` 慢 4~6 倍：每个条件都是一次 `std::function` 调用，编译器无法内联。但 25 纳秒意味着一万个守卫每帧只要 0.25 毫秒。真实游戏里，感知（视线检测、寻路查询）的代价要高出几个数量级，状态机本身的开销可以忽略。

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`，取 5 次中的最快值。测试时机器负载极高（load average 一度超过 170），表中给出了多次运行的范围，结论一致。代码在 `cpp/ai/fsm/fsm_bench.cpp`。

## 状态机的局限

分层状态机解决了重复转移的问题，但随着行为变复杂，仍然会遇到瓶颈：

- **转移是网状的**。每个状态都要知道自己可以去哪里，加一个新状态往往要修改好几个旧状态的转移。
- **复用困难**。"走到某处再做某事"这样的片段，在不同状态里写了一遍又一遍。
- **难以表达"按顺序做几件事"**：先走到门口、开门、进去、关门。用状态机写，每一步都是一个状态，加上失败时的处理，很快就变得很乱。

下一篇的**行为树**正是为了解决这些问题：它把行为组织成一棵树，用"顺序""选择"这样的组合节点表达逻辑，节点之间不再需要互相知道。

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 状态在两个之间来回闪烁 | 两条转移的条件互为反面，在边界附近交替满足 | 加入滞后：进入攻击的距离 1.5 米，退出的距离 2 米（本文的写法） |
| 紧急情况被忽略 | 内层状态的转移先被检查 | 外层优先；把全局事件挂在最外层 |
| 被打断后从头开始 | 状态机不记得之前在做什么 | 历史转移 |
| 退出动作没有执行，计时器、动画残留 | 跨层切换时只退出了叶子 | 退出到最近公共祖先为止，逐层执行退出动作 |
| 一帧内连续切换好几次，行为难以预测 | 转移后立即再次检查 | 每次更新最多一次转移（本文的写法），或者限制次数 |
| 角色多了以后状态机很慢 | 每个角色复制一份完整的定义 | 定义与实例分开，定义只存一份 |
| 加一个全局事件要改所有状态 | 用的是扁平状态机 | 分层：挂在父状态上 |

## 在游戏中的应用

- **角色 AI**：从《吃豆人》的幽灵（追击、分散、受惊三种模式）开始，状态机就是游戏 AI 最常用的结构。很多动作游戏的敌人仍然用分层状态机实现。
- **动画状态机**：Unity 的 Animator、Unreal 的动画蓝图，都是可视化的分层状态机：待机、走、跑、跳各是一个状态，按参数条件切换，还支持子状态机。
- **游戏流程**：主菜单、加载、游戏中、暂停、结算，就是一个状态机。
- **UI、网络连接、关卡事件**：任何"处于某种模式、遇到事件时切换"的逻辑都适合用状态机描述。

## 练习

1. **进入时的计时器**：给 `HfsmDef` 加上"在当前状态停留的时间"，让条件可以写成"在搜查状态超过 3 秒"，从而不再需要在上下文里存 `investigateUntil`。
2. **事件驱动**：现在每帧都检查所有条件。改为由事件触发：`machine.send("noise")` 只检查监听这个事件的转移。比较两种方式在 1 万个守卫、大部分时间没有事件时的开销。
3. **自动展平**：写一个函数，把分层状态机自动转换成等价的扁平状态机（叶子状态 + 展开后的转移），历史转移用复制状态的方式展开。用本文的守卫验证展开结果与 `buildGuardFlat` 的转移数相同。
4. **并行状态**：守卫的移动（巡逻、追击）和武器（装填、开火）是两件独立的事。如果用一个状态机，状态数是两者的乘积。实现"并行区域"：一个复合状态同时激活两个子状态机。
