## 问题：随机，但要"对的随机"

游戏里的随机数无处不在：暴击、掉落、地图生成、AI 决策、洗牌发牌。但"调用一下 `rand()`"会带来一连串问题：

- **无法复现**：玩家报告"种子 12345 的地图第三层有 bug"，你却生成不出同一张地图
- **偷偷有偏**：洗牌算法看起来很随机，某些排列的出现概率却明显更高
- **感觉不公平**：数学上完全正确的 25% 暴击，玩家却总觉得"脸黑"

这一章逐个解决。

## 可复现的随机数生成器

计算机里的随机数几乎都是**伪随机**：由一个确定的算法从"种子"推导出一串看起来随机的数。同一个种子，永远得到同一串数，这恰恰是游戏需要的特性：程序化地图、录像回放、帧同步联机都依赖它。

<Aside type="caution" title="为什么不用标准库">
`rand()` 的范围可能只有 0~32767，质量也参差不齐，还是全局状态，多个系统共享时互相干扰。`std::mt19937` 本身是确定的，但 `std::uniform_int_distribution` 等分布的**实现没有标准化**：同一个种子在 MSVC 和 GCC 上可能得到不同结果。需要跨平台复现时，应该自己掌控从生成器到分布的每一步。
</Aside>

本系列使用 **PCG32**：只有 16 字节状态，速度快，统计质量好，代码不到 20 行：

<CppSnippet file="foundations/random/random.h" region="pcg32" mark={['uint32_t threshold = (~bound + 1u) % bound;  // = 2^32 mod bound']} />

注意 `below` 的写法。直接 `next() % 6` 是**有偏**的：2³² 不能被 6 整除，余下的那部分会让小的点数多出现一点点。正确的做法是把"凑不满一整轮"的那部分结果丢掉重抽。

## 洗牌：一个看起来对、其实错的算法

把一副牌打乱，很多人会这样写：遍历每个位置，和**任意**一个位置交换。

<CppSnippet file="foundations/random/random.h" region="naive-shuffle" />

问题出在计数上：n 张牌，每步有 n 种选择，共 nⁿ 种执行路径，而排列只有 n! 种。6 张牌时是 46656 条路径对应 720 种排列，46656 不能被 720 整除，所以**不可能每种排列概率相等**。

正确的做法是 **Fisher–Yates**：从后往前，每个位置只和"它自己或它前面"的元素交换。这样恰好有 n! 条路径，一一对应 n! 种排列：

<CppSnippet file="foundations/random/random.h" region="shuffle" />

## 加权随机：掉落表

"普通 60%、稀有 10%、传说 1%"这类掉落表，标准做法是预先算好权重的前缀和，抽取时生成一个 `[0, 总权重)` 的随机数，再二分查找它落在哪个区间：

<CppSnippet file="foundations/random/random.h" region="weighted" />

预处理 O(n)，每次抽取 O(log n)。权重表很大且抽取极其频繁时，可以改用 **别名方法**（alias method），抽取降到 O(1)。

演示的 **loot** 页同时显示期望概率（竖线）和实际频率（条形）。抽得越多，二者越接近，这就是大数定律。但在抽取次数少的时候，传说装备的实际频率可能离 1% 很远，这正是玩家抱怨的来源。

### 伪随机分布（PRD）

独立随机的 25% 暴击，连续 15 次不暴击的概率是 0.75¹⁵ ≈ 1.3%。一场战斗打几百刀，几乎每局都会遇到一次"长期脸黑"。

**伪随机分布**（Pseudo-Random Distribution）换了一种规则：第 N 次尝试的触发概率是 `N × C`，一旦触发，N 归零。刚暴击过的下一刀概率很低，越久没暴击概率越高，到 `N × C ≥ 1` 时必定触发。适当选取常数 C，长期平均概率仍然是 25%。

C 没有简单的解析解，但"平均概率"随 C 单调递增，可以二分查找：

<CppSnippet file="foundations/random/random.h" region="prd" />

常用概率对应的 C 值，以及最长可能的连续不触发次数：

| 名义概率 p | 常数 C | 最长连续不触发 |
|---|---|---|
| 5% | 0.00380 | 263 |
| 10% | 0.01475 | 67 |
| 15% | 0.03222 | 31 |
| 20% | 0.05570 | 17 |
| 25% | 0.08474 | 11 |
| 30% | 0.11895 | 8 |
| 40% | 0.20155 | 4 |
| 50% | 0.30210 | 3 |

切到演示的 **crit** 页：两条时间线的暴击率都接近 25%，但独立随机的时间线上有明显的空白和扎堆，PRD 的暴击分布均匀得多。下方直方图中，独立随机的间隔有一条很长的尾巴，PRD 的间隔则集中在 3~6 之间，而且不会超过 12。

<Aside type="tip" title="PRD 也有代价">
PRD 让"连续暴击"变少了，暴击的节奏更可预测。熟练的玩家可以利用这一点，例如先打小兵"攒概率"，再去打英雄。是否使用、用在哪些机制上，是设计决策而不仅是技术决策。
</Aside>

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 每次运行结果都一样，或每次都不同 | 种子固定写死，或每次都用当前时间 | 种子作为显式参数传入，需要随机时再取时间或系统熵 |
| 骰子 1~2 点出现得稍多 | `next() % n` 的取模偏差 | 用拒绝采样的 `below(n)` |
| 洗牌结果有偏 | 和任意位置交换 | 使用 Fisher–Yates |
| 回放和原局对不上 | 多个系统共用一个随机数生成器，调用顺序变了 | 每个系统使用独立的生成器（不同 stream） |
| `nextFloat()` 偶尔返回 1.0 | 用 `next() / 4294967295.0` 得到闭区间 | 只取高 24 位再乘以 2⁻²⁴，得到 [0, 1) |

## 在游戏中的应用

- **程序化生成**：Roguelike 的种子地图，本质上就是把种子交给 PCG 这类生成器（见第四卷）。
- **帧同步联机**：所有客户端用同一个种子、同样的调用顺序，才能得到同样的随机结果。
- **暴击、闪避、触发类被动**：PRD 是 MOBA 和 ARPG 中的常见做法。
- **抽卡保底**：在加权随机之外再加一层"N 次未出必出"的计数器，原理和 PRD 相近。
