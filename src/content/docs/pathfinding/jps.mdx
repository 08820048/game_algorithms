## 问题：A* 在空地上做了太多无用功

上一篇的优化让每次展开更便宜、展开得更少，但 A* 还有一种浪费，在**空旷的网格**上尤其严重。

从 A 走到 B，如果中间是一片空地，代价相同的最短路径往往有几十上百条：先斜后直、先直后斜、斜直交替……A* 无法区分它们，只能把这些路径上的格子统统加入开放列表、逐个展开。这就是**路径对称性**（path symmetry）。

**JPS**（Jump Point Search，跳点搜索）由 Daniel Harabor 和 Alban Grastien 在 2011 年提出。它的思路是：既然这些路径都一样好，那就**只保留一种**，沿着直线一口气"跳"过去，只在可能需要拐弯的格子停下。这些格子叫做**跳点**。

<JpsFigure label="图 1.6" caption="左：A 到 B 之间代价相同的路径有很多条，朱红色是其中一条。右：横走到 x 时，身后的墙挡住了 p → n 的斜线，n 只能经过 x 最快到达，所以 x 必须停下来，n 是 x 的强迫邻居。" />

## 准备：8 方向网格

JPS 是为**代价统一的 8 方向网格**设计的，和前几篇的地图有两点不同：

- **8 方向移动**：除了上下左右，还可以斜着走。直走代价 10，斜走代价 14（约等于 10√2，用整数避免浮点误差）。
- **没有地形代价**：每个格子要么能走，要么是墙。

斜走还有一条规则：**不能切墙角**。从一个格子斜向移动时，两侧相邻的直走格子都必须能通行，否则单位的模型会穿过墙角。启发函数相应地换成八方向距离：先斜走 `min(dx, dy)` 步，再直走剩下的。

几个值得做的小实验：

1. 切到 **a\***，观察起点附近：A* 把左边整个房间都展开了，每个格子都连着一条短短的"父节点线"。切回 **jps**，同一片区域只剩几条长长的直线。
2. **单步**执行 JPS。每一步都会从当前跳点出发，沿几个方向扫出很长的直线，再在少数几个格子上停下。
3. 用 **wall** 在空地上随手画一些零散的墙点。墙点越碎，跳点越多，JPS 的优势越小。

## 跳跃

JPS 的核心是一个 `jump` 函数：从某个格子出发，沿一个方向一直走，直到遇到以下三种情况之一：

- **撞墙或走出地图**：这个方向没有跳点，返回失败。
- **到达终点**：终点本身就是跳点。
- **发现强迫邻居**：这个格子必须停下来，它就是跳点。

### 强迫邻居

什么时候必须停下？看图 1.6 的右半部分。沿着中间一行向右走，从 p 走到 x。正常情况下，x 上方的格子 n 可以直接从 p **斜着**到达，不需要经过 x，所以展开 x 时不必考虑它。

但如果 p 的上方是墙，从 p 斜着去 n 就会切墙角，不允许。到达 n 的最短路线只能经过 x，于是 x 就成了一个"岔路口"：需要停下来，把向上的方向也考虑进去。n 被称为 x 的**强迫邻居**（forced neighbor）。

判断条件非常简单：**侧面的格子能走，而它身后那一格是墙**。

### 斜着跳

斜着跳时，每走一步，都先沿它的两个直走分量（比如向右下跳时，分别向右、向下）各跳一次。只要任何一个方向能找到跳点，当前格子本身就是跳点，因为从这里拐弯可能通向一条更好的路线。

<CppSnippet file="pathfinding/jps/jps.h" region="jump" mark={['if (jump({c.x + dx, c.y}, dx, 0, &unused) || jump({c.x, c.y + dy}, 0, dy, &unused)) {']} />

<Aside type="note" title="关于切墙角">
Harabor 和 Grastien 的原始论文允许切墙角，强迫邻居的判断条件与这里不同：在那种规则下，斜走也会产生强迫邻居。本文采用的是游戏中更常见的"不切墙角"规则，对应的判断条件参考了开源库 PathFinding.js。两种规则不能混用，否则会漏掉最优路径。
</Aside>

### 剪枝：从哪个方向来，就只看哪些方向

展开一个跳点时，也不需要尝试全部 8 个方向。从左边横着来的，没有必要再往回看；从左上斜着来的，只需要继续斜走，或者沿它的两个分量直走。

## 实测：JPS 不是总能赢

在两种 256×256 的地图上，用同一批起终点对比 A* 和 JPS：

| 地图 | A* 展开 | JPS 展开 | JPS 扫描 | JPS 相对 A* 的速度 |
|---|---|---|---|---|
| 房间：大片空地 + 矩形障碍 | 1534 | 63 | 13531 | 约 2~3 倍 |
| 噪声：每格 25% 概率是墙 | 3917 | 2049 | 13284 | 约 1~1.5 倍 |

两点值得注意：

- 在房间地图上，JPS 展开的节点少了 **24 倍**，速度却只快了 2~3 倍。原因在"扫描"那一列：JPS 省掉了堆操作，但跳跃时要逐格检查墙，扫描的格子数甚至远多于 A* 展开的格子。这些检查比堆操作便宜得多，但并不是免费的。
- 在零碎障碍很多的地图上，到处都是强迫邻居，跳不了多远就要停下，JPS 几乎退化成 A*。

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`，取 5 次运行中最快的一次，多次运行之间波动较大，表中给出的是范围。代码在 `cpp/pathfinding/jps/jps_bench.cpp`。为了与 A* 公平比较，这里的两种实现都没有使用上一篇的缓冲区复用。
</Aside>

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 路径偶尔不是最短的 | 强迫邻居规则与切墙角规则不匹配 | 两者必须配套：允许切墙角就用原论文的规则 |
| 在带地形代价的地图上结果错误 | JPS 依赖"直线上每一步代价相同"的对称性 | 只用于代价统一的网格；有地形时用 A* |
| 比 A* 还慢 | 地图障碍零碎，跳点密集 | 先在真实地图上测量；考虑预处理版本 JPS+ |
| 斜着跳时栈溢出 | 递归实现的 `jump` 在大地图上层数很深 | 直走用循环，只有斜走调用一层直走跳跃（本文写法） |
| 单位沿跳点走时穿墙 | 跳点之间是直线或斜线，但单位按任意角度直线移动 | 跳点之间只沿 8 个方向走，或者先展开成逐格路径 |

## 在游戏中的应用

- **网格类游戏**：Roguelike、战棋、塔防、俯视角射击，只要地图是代价统一的网格，JPS 都可以直接替换 A*，路径完全相同。
- **JPS+**：离线预计算每个格子在 8 个方向上到下一个跳点（或墙）的距离，运行时直接查表，通常还能比 JPS 再快数倍。代价是地图改变后需要重新计算受影响的部分，适合静态地图。
- **可破坏地形**：地图会频繁变化时，JPS 不需要任何预处理，比 JPS+ 和[下一篇的导航网格](/pathfinding/navmesh/)更容易维护。
