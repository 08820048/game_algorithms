## 问题：两百个士兵，同一个目的地

即时战略游戏里最常见的操作：框选一大群单位，右键点击地图上的某个位置。

用前面学过的方法，就是给每个单位各跑一次 A*。两百个单位就是两百次寻路，而且只要目标一变（玩家又点了一下，或者追击的敌人移动了），全部重来。更麻烦的是，两百条路径往往挤进同一个路口，单位互相推挤、卡死。

换个角度想：这两百个单位的**目的地是同一个**。与其从每个单位出发找路，不如**从目的地出发**，一次性算出"地图上每个位置该往哪个方向走"。这就是**流场**（flow field）。

<Aside type="tip" title="似曾相识">
1.1 的 BFS 一节提到过"一对多寻路"，1.2 讲过 Dijkstra 地图。流场就是把这个想法做成一套完整的系统：再加上方向和移动，就能驱动整支军队。
</Aside>

## 三层"场"

流场寻路由三层数据组成，每一层都由上一层计算得到：

| 层 | 每个格子存什么 | 怎么得到 |
|---|---|---|
| 代价场（cost field） | 走进这个格子的代价 | 地图本身：平地 1、森林 3、沼泽 6、墙不可通行 |
| 积分场（integration field） | 从这里走到目标的最小总代价 | 从目标出发做一次 Dijkstra |
| 流场（flow field） | 一个方向 | 指向积分值最小的邻居 |

<Demo name="flowfield" title="流场寻路" label="图 1.9" caption="240 个单位共享同一张流场。底色是积分场（越深离目标越近），箭头是流场。拖动 G 改变目标，或用画笔修改地形，流场会立即重算，所有单位马上改道。cost 开关显示积分值，spawn 重新生成单位。" />

几个值得做的小实验：

1. 等单位走到 G 附近后，**把 G 拖到地图另一头**。所有单位立刻掉头，没有任何"重新寻路"的停顿，因为流场只需要重算一次。
2. 打开 **cost**，看积分值如何从 G 向外增长：经过森林和沼泽时增长得更快，所以箭头会绕开它们。
3. 用 **wall** 把左侧墙下方的缺口堵死：被隔开的区域里箭头全部消失，单位停在原地。再用 **erase** 在墙上另开一个口子，箭头立刻整体转向新的出口。
4. 单位走进沼泽时会明显变慢：移动速度除以了格子的代价。

## 积分场

积分场就是从目标出发的 Dijkstra。这里换成 8 方向移动，斜走代价为直走的 1.4 倍，同样不允许切墙角：

因为是从**目标**出发，积分场与单位数量无关。一个单位还是一千个单位，都只算这一次。

有了积分场，每个格子只要看一眼周围 8 个邻居，指向数值最小的那个：

<CppSnippet file="pathfinding/flowfield/flowfield.h" region="flow" />

这里有一个很重要的性质：**积分场除了目标之外没有局部最小值**。任何一个可达的格子，它的积分值都是"某个邻居的积分值 + 走过去的代价"，所以一定有一个邻居比它小。顺着箭头走，积分值严格下降，最终一定到达目标。

<Aside type="note" title="为什么不用势场">
另一种常见的"场"是势场：目标产生吸引力，障碍物产生排斥力，单位沿合力方向移动。它简单直观，却有一个致命问题：单位会卡在凹形障碍物里的局部最小值上，永远出不来。积分场是由真实的最短路径代价构成的，从根本上避免了这个问题。
</Aside>

## 实测：多少个单位才值得用流场？

在 256×256 的随机地图上（20% 墙、15% 森林、7% 沼泽），所有单位去同一个目标：

| 方法 | 耗时 |
|---|---|
| A*（1.4 的 `Pathfinder`），1 个单位 | 0.2 ms |
| A*，10 个单位 | 2.6 ms |
| A*，100 个单位 | 26 ms |
| A*，1000 个单位 | 290 ms |
| Dijkstra 地图（4 方向），任意数量单位 | 2.9 ms |
| 积分场 + 流场（8 方向），任意数量单位 | 6.5 ms |

一次全图 Dijkstra 的开销大约相当于 10~25 次 A*。超过这个数量，流场就开始占优；到了一千个单位，差距超过 40 倍。反过来，如果只有几个单位，或者每个单位的目的地都不同，A* 仍然是更好的选择。

<Aside type="note" title="测试环境">
Apple M3，Apple clang 21，`-O2`，取 5 次运行中最快的一次。代码在 `cpp/pathfinding/flowfield/flowfield_bench.cpp`。
</Aside>

## 常见陷阱

| 问题 | 原因 | 解决 |
|---|---|---|
| 单位走"之"字形 | 8 方向的箭头只能表示 8 个角度 | 双线性插值采样；或者对能直接看到目标的格子，让箭头直接指向目标 |
| 单位挤在墙角卡住 | 分离力把单位推进墙里，墙又把它推回来 | 碰撞后去掉朝墙的速度分量；墙边的格子适当提高代价 |
| 所有单位挤在目标点上抖动 | 每个单位都想站在同一个点 | 到达目标附近后切换为"停止 / 排阵型"状态 |
| 大地图上内存和计算量太大 | 每个目标一张全图大小的场 | 把地图分块，只在路径经过的块里计算（见下文） |
| 大型单位卡在窄路口 | 积分场把单位当作一个点 | 按单位体型分别计算代价场，窄于单位的格子视为不可通行 |

## 在游戏中的应用

- **即时战略游戏**：《最高指挥官 2》（Supreme Commander 2）是流场寻路在商业游戏中最著名的应用之一。它把地图分成若干块，先在块之间做高层寻路，只为路径经过的块计算流场，并把结果缓存起来。
- **塔防游戏**：所有敌人去同一个终点，玩家每放一座塔就改变一次地图，流场的重算开销与敌人数量无关，非常合适。
- **大规模人群**：体育场散场、城市疏散这类模拟，往往有几个出口，用多源积分场就能让每个人走向最近的出口。
- **AI 的"安全地图"**：把危险源作为目标计算积分场，再取反，就得到了"往哪里跑最安全"。

## 练习

1. 实现"视线优化"：对于能直接看到目标的格子（用 1.4 的 `lineOfSight`），让箭头直接指向目标，而不是 8 个方向之一。比较单位轨迹的变化。
2. 实现多目标：把三个出口都作为 `integrationField` 的源点，让单位自动走向最近的出口。
3. 把分离力的两两比较改为均匀网格分桶，测量 2000 个单位时每帧的耗时。
4. 为每个单位记录"卡住的时间"：如果 1 秒内几乎没有移动，就临时提高附近格子的代价，重算流场。这能缓解拥堵吗？
